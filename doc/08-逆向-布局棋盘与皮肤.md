# 08 逆向：布局、棋盘与皮肤资源

范围：豆包输入法（`com.bytedance.android.doubaoime`）的键盘布局描述、棋盘类型、键位几何、
工具栏与候选栏、皮肤资源。素材是 jadx 1.5.1 反编译源码、APK 资源、`libkeyboard.so` 的
符号与字符串；没有新增真机实验。

证据等级：**A** = 直接读到的代码/资源/运行时记录；**B** = 反编译可见但本次未运行验证；
**C** = 推断（写明依据）。源码路径相对 `/tmp/doubao-ime/src/sources`，资源路径相对
`/tmp/doubao-ime/src/resources`。

## 1. 布局是怎么描述出来的

**皮肤根目录**：`assets/skin/` 下只有 `default/` 一套，结构为
`input_main.xml`、`translate_main.xml`、`style.xml`、`layout/*.xml`、`drawable/*.png`、
`dark/drawable/`、`land/style.xml`、`floating/style.xml`、`values/{colors,dark_colors,transparent_colors}.xml`、
`2x|3x|3.5x/style.xml`（A，`resources/assets/skin/default/`）。

**主窗口**只留一个空棋盘容器，注释写明"当前键盘按需创建，其余键盘在首帧后逐帧补齐"：
`input_main.xml` 的 `<InputBoardLayout name="input_kbd_table" width="match_parent" height="match_parent"/>`（A）。
棋盘本体都由 native 按当前棋盘类型加载对应 XML 并绘制（B：Java 源码里没有
`English26Layout`、`Pinyin26Layout`、`ButtonChar`、`ButtonSwitchBoard`、`CandListLayout`
任何一个类，`libkeyboard.so` 里有 `ui::English26Layout`、`ui::Pinyin26Layout`、`ui::Pinyin9Layout`、
`ui::StrokeLayout`、`ui::NumberLayout`、`ui::SymbolLayout` 等符号）。

**XML schema**（A，`layout/input_kbd_english26.xml`、`style.xml`）：

| 标签 / 属性 | 含义 | 证据 |
|---|---|---|
| `Window` → `English26Layout` / `Pinyin26Layout` / `Pinyin9Layout` / `StrokeLayout` / `SymbolLayout` / `NumberLayout` / `NumberSymbolLayout` / `SwitchLayout` / `SettingsLayout` / `MoreCandsLayout` / `BoardLayout` | 棋盘根节点，一个标签对应一种棋盘 | A（标签名与文件名）|
| `keycode` | 引擎键码。字母键写 `Q`/`q`；气泡里用 `0x1051`（大写）、`0x0051`（小写）、`0x3031`（数字）区分大小写与全角数字 | B |
| `commitstr` | 直接提交的文本，如 `commitstr="q"`、`commitstr="1"` | A |
| `can_slide_cursor="true"` | 只在 `English26Layout` 上出现；开启"在键盘上滑动移光标" | A（仅一处：`layout/input_kbd_english26.xml:4`）|
| `width_weight` / `height_weight` | 行内/列内权重；`style.xml:293` 注释"宽度权重10 是 10 个按键 100/10 得到" | A |
| `class` / `class_adaptive` | 样式类与自适应覆盖类；`class_adaptive` 会覆盖 `class` 的同名属性（推断依据见第 2 节的 `target`）| B |
| `target` | `ButtonSwitchBoard` 的目标棋盘号，见第 2 节 | B |
| `ficon_text` / `fusiyin_*` / `long_press_bubble_*` | 副丝印、上滑气泡、长按气泡的文本与键码序列 | A |
| `userdata` / `slidable_control` | 9 键棋盘的数据标记与可滑动控件名 | A |
| `name` | 控件名，Java 侧按名字找到按钮（如 `btn_morecand`）| A |

**共有 12 个棋盘布局文件**（A，`assets/skin/default/layout/`）：`input_kbd_english26`、
`input_kbd_pinyin26`、`input_kbd_pinyin9`、`input_kbd_number`、`input_kbd_number_from26`、
`input_kbd_number_symbol_en`、`input_kbd_number_symbol_cn`、`input_kbd_symbol`、
`input_kbd_stroke`、`input_kbd_more_symbol`、`input_kbd_bihua`、`input_kbd_wubi`。
其中 `bihua`、`wubi`、`more_symbol` 是空的 `<BoardLayout>` 占位（A），内容由 native 或
Java 视图另画（手写板是 Java 的 `HandWritingBoardView`，B）。

**怎么选中一套**：native 的 `ui::WindowBoardView::SetBoardType(InputBoardType, ...)` 决定，
Java 通过 `switchKeyboard(int)`（`KeyboardJni.java:6322`）转发，调用点只有
`kHandwrite`、`kNumber`、`kSymbol` 三处（`n7/a.java:462`、`InputViewRoot.java:1854`、`:1866`，B）。
资产路径由 `EnvironmentImpl.b()` 拼出：`skin/default/` + 密度桶 + 横竖屏 + 主题 + 相对路径，
任一目录缺失就往下一层回落（`input/environment/impl/EnvironmentImpl.java:470`；
密度桶 `2x/3x/3.5x` 见 `input/basic/AppGlobalsImpl.java:162`，横屏 `land`/悬浮 `floating`
见 `:487`，深色/透明见 `:642`）。

## 2. 棋盘类型全表

引擎侧是 native 枚举 `ui::InputBoardType`（`libkeyboard.so` 符号 `GetBoardType`、
`SetBoardType`、`GetBoardTypeName`），Java 侧有一份同名的 15 项枚举
（`KeyboardJni.java:425`）。另有一个 7 项、带显式值的 `KeyboardInputMode`
（`input/constants/KeyboardInputMode.java:6`：`PY26(0), PY9(1), ENGLISH26(2), DOUBLE_SPELL(3),
HANDWRITING(4), STROKE(5), WUBI(6)`），不要与棋盘号混用（A：显式值；C：用途区分）。

| 值 | `InputBoardType` | 对应布局文件 | 证据 |
|---|---|---|---|
| 0 | kPinyin26 | `input_kbd_pinyin26.xml` | A（运行时记录 + target）|
| 1 | kPinyin9 | `input_kbd_pinyin9.xml` | B |
| 2 | kEnglish26 | `input_kbd_english26.xml` | A（运行时记录）|
| 3 | kSymbol | `input_kbd_symbol.xml` | B（符号键 `target="3"`）|
| 4 | kMoreSymbol | `input_kbd_more_symbol.xml`（空占位）| B |
| 5 | kNumber | `input_kbd_number.xml` | A（点 123 后读到 5）|
| 6 | kHandwrite | `input_kbd_bihua.xml`（空占位）+ `HandWritingBoardView` | C（按名与空文件推断）|
| 7 | kWubi | `input_kbd_wubi.xml`（空占位）| C |
| 8 | kNumberSymbolEn | `input_kbd_number_symbol_en.xml` | B（英文 123 键 `target="8"`）|
| 9 | kNumberSymbolZhCn | `input_kbd_number_symbol_cn.xml` | B（拼音 26 的 123 键 `target="9"`）|
| 10 | kNumberFrom26 | `input_kbd_number_from26.xml` | B（数字符号页 `target="10"`）|
| 11 | kStroke | `input_kbd_stroke.xml` | B（按名）|
| 12 | kBoardSwitch | `input_switch_keyboard.xml`（`userdata="board_switch"`）| B |
| 13 | kMoreCand | `input_more_cand.xml` | B |
| 14 | kSettings | `input_settings.xml` | B |

运行时锚点只有三个：26 键字母面读 0、点 123 读 5、点返回读 0
（`app/.../BoardGuard.java:18-20` 的实测记录；本轮未复跑，按 A 计）。`switchKeyboard` 的
Java 调用点也只用到 3/5/6。**11–14 的 `target` 与枚举顺序对不上**：设置页"键盘选择"按钮写
`target="11"`（枚举 11 = kStroke），工具栏"更多候选"写 `target="12"`（枚举 12 = kBoardSwitch），
logo 键写 `target="13"`（枚举 13 = kMoreCand）。三者更像另一套窗口号，而不是 `InputBoardType`；
键盘布局内的 3/5/8/9/10 则完全对得上（B 对 3/5/8/9/10，C 对 11–14，见"未证实"）。

`getCurrentKbdType()` 是 `KeyboardJni` 的实例方法（`KeyboardJni.java:5951`），全库唯一语义化
用法是跟 `kHandwrite.ordinal()` 比较（`KeyboardJni.java:4812`）。同一实例上还有
`getKeyboardType()`（返回 `key_eng` 这类字符串，`n9/u.java:1025`）、`getBoardEventName()`
（埋点名，`KeyboardJni.java:5933`）、`IsEnglishKeyboard()`（`:5802`）。

## 3. 键位几何

**横向**：每行 `width_weight` 求和，`unit = 视图宽 / 行权重和`。26 键三行字母区都是 100：
第 1 行 10×10；第 2、3 行 15 + 70 + 15（`input_kbd_english26.xml:5/48/102`，A）。
1080 宽时 `unit = 10.8`，单键格 108 px，按键留白 `margin="2.25,4.75,2.25,4.75"`
（`style.xml:289`）——左右各 2.25、上下各 4.75 个设计单位。

**纵向**：四行等高。`English26Layout` 的四行写 `height_weight="match_parent"`，
`Pinyin26Layout` 的四行写 `height="match_parent"`，两种写法在真机上都渲染成四等分（A：键盘实际可用；
B：两种属性等价）。棋盘类 `cls_input_kbd` 带
`padding1x="0,57,0,1.25"`（`style.xml:743`）与 `inset="2.5,-4.75,2.5,0"`（`:727`），
即键区上边距 57 − 4.75 = 52.25、下边距 1.25（设计单位）。

**换算成像素**：布局数值不是 dp，是按 1080 宽这一档设计出来的数值；缩放因子来自
`InputViewModel.f8469a = min(屏宽,屏高)/360`（上限 4.0，`InputViewModel.java:766-779`），
`je.a.q(x) = round(f8469a * x)`（`je/a.java:329`）。真机 1080×909 上按模块的记录反推：
键区行高 `(909 − 151) / 4 = 189.5`，与 `(909 − 97.5 − 57 + 4.75 − 1.25)/4 = 189.5` 吻合，
即顶部 151 里约 52 是上面的 padding、约 99 是候选栏/工具条在棋盘内占的高度（C，算术自洽，
两个量的拆分未经实验）。

**有没有官方"坐标 → 键"查询接口：没有。** Java 侧不存在 `getKeyAt`/`hitTest`/`findKey`
一类方法（A：全库 grep 无结果）；`libkeyboard.so` 的 JNI 导出里也没有任何坐标入参的函数，
只有 `ButtonBase::GetKeyCoordinate(const tagPOINT&)` 这种 C++ 内部方法（B：符号表）。
命中测试完全在 native 内，触点从 `KeyboardView.onTouchEvent` 直接交给
`nativeTouch(mNativeViewId, x, y, action, 时间)`（`KeyboardView.java:1287-1341`，A）。

**能问引擎的量**只有这几个：`getCurrentKbdType()`（棋盘号）、`getToolbarHeight()`
（`KeyboardJni.java:5985`，native `ui::WindowBoardView::GetToolbarHeight()`，B；返回单位未验证）、
`getKeyboardType()`、`getBoardEventName()`。另外 `getAssetsMgr()`
（`KeyboardView.java:498`）能在输入法进程里直接读到 `skin/default/...` 下的布局与样式 XML（A）。

## 4. 工具栏与候选栏

- 工具栏有 5 个窗口布局：`input_toolbar_idle.xml`（空闲）、`input_toolbar_typing.xml`
  （输入中，含拼音组合区 `Composition` + 候选列表 + 更多候选按钮）、`input_toolbar_quickinput.xml`、
  `input_toolbar_tip.xml`、`input_toolbar_ai_writing.xml`；状态机是 `ToolbarState`
  （`KeyboardJni.java:551`：`kToolbar/kCandList/kQuickinput/kTip/kAiWriting`，A）。
- 可定制性在 native：`getToolbarConfig()` 返回 JSON（`KeyboardJni.java:5983`），Java 只解析
  了 `alignment` 一个键（`input/popup/g.java:42`），其余交给 native 的
  `toolbar_config_manager.cpp`（`libkeyboard.so` 字符串里有 `alignment`、`buttons`、`left`、
  `right`，B）。改动入口：`enterCustomizeToolbar()`、`customizeToolbarButton(boolean, String)`、
  `confirmCustomizeToolbar()`、`exitCustomizeToolbar()`、`reorderToolbarButtons(String[])`
  （`KeyboardJni.java:5868/5874/5894/5898/6169`，A）。按钮名就是布局里的 `name`，如
  `btn_toolbar_clipboard`、`btn_toolbar_translate`（A，`input_toolbar_idle.xml` 与 `.so` 字符串）。
- 候选栏同样是 native 画的：布局里只有 `<CandListLayout name="cand_list" class="cls_cand_list"/>`
  一个占位（`input_toolbar_typing.xml`），Java 没有任何候选列表模型；点击由
  `onCandidateBarItemButtonDown/Up(...)` 把候选文本与索引回传 native
  （`KeyboardJni.java:6085/6087`，调用点 `n7/a.java:934/517`，A）。
- `getCandlist()`（`KeyboardJni.java:5937`）声明了 JNI，但 **Java 侧调用点未找到**（A：全库
  grep 只有声明），用途未证实。

## 5. 皮肤

- **格式**：不是压缩包，是 assets 目录树（A）。一层 XML（`style.xml` 定义 `Class`/`Font`/颜色
  引用）+ 每窗口一个布局 XML + PNG 位图 + `values/colors.xml` 等。
- **可以只换部分资源**：`EnvironmentImpl.b()` 按 `密度 / 横竖屏 / 主题` 逐级拼路径并回落，
  所以覆盖目录里只放要改的文件即可（`EnvironmentImpl.java:470`，B）。例如
  `land/style.xml` 只改了 `padding1x` 与 123 行宽度（`assets/skin/default/land/style.xml`，A）。
- **运行时改皮肤没有 Java 入口**：没有下载、解压、切换皮肤目录的代码，皮肤名固定拼成
  `skin/default/`（A）。native 侧有一个字符串 `/files/data/skin`（`libkeyboard.so`），
  暗示存在外部皮肤目录，但读写逻辑未见（C，见"未证实"）。
- **模块不重打包能影响渲染的路**：① 钩 native 回调到 Java 的绘制方法——`drawText`、
  `fillRect`、`drawRect`、`drawImage`、`drawLine`、`drawTouchTipBubble` 等都由 native 调进 Java
  （`KeyboardView.java:853-1025`，A），可在 Java 侧改色/叠加；② 往 `InputViewRoot` 上叠一层
  自绘 View；③ 若 `/files/data/skin` 真被 native 读取，投放同名皮肤目录即可（未验证，风险最高）。

## 6. 对模块的可用性评估

| 可用的信息 | 从"自己算"变成"问引擎/问资产"的收益 | 风险 |
|---|---|---|
| `getCurrentKbdType()` | 已经用上：多一种棋盘号就能多武装/少武装一块棋盘，不必靠几何猜 | 11–14 的语义未证实，按枚举硬编码会把符号页误判成笔画页 |
| `getToolbarHeight()` | 顶部非键区（现在写死 151/909）可直接读，换分辨率、横屏、悬浮键盘都不用重标定 | 返回单位与"是否含棋盘 padding"未验证，读错会让整块几何偏移 |
| `assets/skin/default/layout/*.xml` + `style.xml` | 行权重、按键留白、`padding1x`、`inset` 都能在运行进程里读到（`getAssetsMgr()`），可把常量表换成按棋盘解析 | 解析器要自己写，且 `match_parent` 与 `class_adaptive` 的覆盖顺序只能靠实测确认 |
| `switchKeyboard` / `InputBoardType` | 可以主动切棋盘做自检（例如切到数字面核对几何），不必人工点 | 切棋盘会打断用户输入，不能在正式路径上用 |

**最值得改的一处**：把 `Geometry` 的 `STRIP_FRAC = 151/909` 换成运行时从
`skin/default/layout/input_kbd_english26.xml` 的 `padding1x`/`inset` 与
`getToolbarHeight()` 推出来的顶部偏移，行高仍按四等分算。当前这个常数只在一台 1080×909、
候选栏已出现的机器上成立；横屏 `padding1x="0,50,0,0"`、悬浮 `padding1x="2,45,2,0"`
（`land/style.xml`、`floating/style.xml`，A）都会让它偏。收益是换形态不用重标定，
风险是 `getToolbarHeight()` 的语义没验证过——先做一次真机对照（读到的值与 151 的差值），
对不上就退回只解析 XML。

## 7. 未证实

1. **11–14 的棋盘号语义**：枚举顺序与设置/工具栏里的 `target` 冲突。要么 native 枚举在
   kStroke 之后与 Java 声明顺序不同，要么这些面板用的是另一套窗口号。没有运行时采样，不下结论。
2. **`getCurrentKbdType` 到底返回哪个枚举**：0/2/5 同时符合 `InputBoardType` 与
   `KeyboardInputMode` 的前几项，只有"点 123 得 5"能排除后者（`KeyboardInputMode` 的 5 是
   STROKE）。按 `InputBoardType` 处理是推断（C），不是证明。
3. **`target` 的覆盖优先级**：`cls_button_123` 自带 `target="5"`，元素上写 `target="9"`，
   自适应类 `cls_26key_button_123_width_adaptive_s` 又写 `target="5"`（`style.xml:929/1014`）。
   真机上读到 5，说明自适应类生效、元素属性被覆盖，但"元素 > class_adaptive"的通用顺序
   没有逐条验证。
4. **`/files/data/skin` 是否可用**：只有字符串，没有读写代码、没有目录样例。
5. **`getToolbarHeight()` 的单位与口径**：未找到调用点，未运行时读到值。
6. **`bihua` / `wubi` / `more_symbol` 三个空布局由谁绘制**：只确认了文件为空。
7. **按键命中用的是格宽还是可见键面**：`ButtonBase::GetKeyCoordinate` 存在，但入参与返回
   未反编译；模块的几何按格中心对齐，边界处的判定没有实验数据。
