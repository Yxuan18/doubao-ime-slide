# 逆向观察：豆包输入法的体验决策，与模块的四处不一致

范围：豆包输入法 1.5.3（`com.bytedance.android.doubaoime`）的设置体系、反馈、可发现性与文案，以及 `app.xuan.doubaoslide` 与原生行为的偏差。

证据等级：**A** = 截图实测或直接读到的资源/代码事实；**B** = 反编译可见但未运行验证；**C** = 推断（写明依据）。截图只用于读界面结构，不引用任何聊天内容、号码或人名。

## 1. 设置体系

设置主页面由 `res/layout/fragment_settings_main.xml` 定义，文案来自 `res/values/strings.xml`，默认值来自 `res/xml/settings_preferences.xml`。`settings_page/` 里只有 `ImeZLinkRouterSettingsPage`（从外部 schema 拉起设置页），实际界面在 `fragment/settings/` 与 `SettingsActivityNext`。以下条目名是资源原文。

| 分组 | 条目（titleText） | 副标题 | 默认 | 性质 |
|---|---|---|---|---|
| 语音输入 | 语音转文字 `voice_input_title` | 标点显示、离线语音等 | — | 入口 |
| 语音输入 | 语音口令 `voice_input_action_title` | 通过说出指定词语来执行操作 | 关 | 需要决定 |
| 键盘输入 | 键盘类型 `kbd_layout_multiple_input_type_title`、布局与显示 `kbd_layout_title` | 9键、26键、手写键盘、双拼键盘等；键盘布局、外观等 | — | 需要决定 |
| 键盘输入 | 模糊拼音 `fuzzy_title` | 设置打字习惯，如z=zh in=ing n=l | 关 | 需要决定 |
| 键盘输入 | 智能联想 `intelligent_association_title`、输入预测类型 `input_prediction_type_title` | 根据上文提供的文字、表情、符号等推荐；联想、表情、颜文字推荐等 | 开 | 默认就对 |

| 辅助输入 | 超级互传 `super_transfer_title`、剪切板 `clipboard_title`、词库管理 `lexicon_management_title` | 跨设备复制粘贴文字或图片 | 剪切板历史默认关 | 需要决定 |

首屏另有三个一级开关：云端联想输入 `cloud_title`（默认开）、离线语音输入 `use_offline_asr`（默认关）、AI聊天助手 `key_aichat_title`（默认未开启，配置值 `-1`）。按键反馈的子项：按键响应模式（`打字跟手优先` / `首选质量优先`，默认后者）、按键声音（默认关）、按键震动（默认关）、按键弹泡(仅全键)（默认开）、上滑输入数字符号 `fusiyin_enable_title`（默认关）。默认值见 `settings_preferences.xml` 的 `app:defaultValue`。（A）

两点值得抄：

1. **把"默认就对"的项藏进二级页，把"要用户决定"的项留在首屏。** 智能联想、按键弹泡、云端联想默认开；验证码、通讯录、剪切板、AI 助手全部默认关。默认值本身就是产品判断：能力默认开，数据默认关。（A，默认值）
2. **"按键响应模式"把技术取舍翻译成人的取舍。** 不是"候选刷新 50ms / 100ms"，而是 `打字跟手优先` 对 `首选质量优先`，副标题各自说明代价——"首选结果质量可能受到影响"对"跟手性可能会受到影响"。（A，文案；B，与 `candidate_delay_refresh` 的映射见 `cd/b.java`）

值得警惕：隐私与权限排在第三组，输入模式、数据上传要滑过语音和键盘才看得到；首屏先给能力、后给边界。模块若照抄分组顺序，会把"装了什么"放在"读什么数据"前面。（C，按 layout 顺序推断）

## 2. 反馈设计

**即时的（按下即发生）**

- 按键音效与振动走两条通道：`KeyboardJni.PlayKeyClick(...)` 与 `UserInteractiveManagerNext.b(...)`（音效 `AudioManager.playSoundEffect`，振动按 `KeyVibrate` 档位分发到后台 executor），都在按键处理时触发；两者默认都关，原生键盘默认是安静的。（B，代码路径可见，时序未运行验证；A，默认值）
- 触摸提示气泡由 `KeyboardView.drawTouchTipBubble` 绘制，native 侧在收到 `nativeTouch(0)` 后调用，属于按下反馈；设置项 `bubbles_title` 写作"按键弹泡(仅全键)"，默认开。（A，代码 + `doc/01` 调用序列 + 默认值；B，截图中气泡与长按浮层的边界未逐帧分清）

**延迟的（有时延或异步）**

- 候选刷新 `candidate_delay_refresh` 默认 50，质量优先模式走 100ms；50ms 内看不到候选是设计内，不是卡顿。（A，默认值与 `cd/b.java`）
- 长按浮层：`KeyboardView.LONG_PRESS_TIMEOUT = 500`，到点发 `nativeTouch(-1)`，引擎靠这次 LEAVE 画出三格浮层的第二格。（A，代码 + `doc/01` 的调用序列实测）
- 语音与整理：`asr_start`「正在倾听 点击结束」→ `asr_recognize`「识别优化中」→ `asr_in_work_tip`「语音处理中，请稍等」；`asr_text_organizing`「智能整理中」、`committing`「提交中...」。（A，字符串；B，切换时机未运行验证）

**豆包怎么处理"不确定"**

它不把不确定藏起来，而是分层命名当前阶段：在听、在识别、在处理各有一句，对应三种等待原因；网络切换这种用户看不见的动作也主动说出来——`asr_switch_cell_setting_guide_text`「无线网络弱，已切换移动网络优化识别」。失败按原因分：`asr_no_voice_error_tip`「没听清，请重新开始」、`asr_service_error_tip`「服务端异常，请重试」、`asr_start_record_error_tip`「话筒被占用 请稍后重试」，取消和重试从不共用一句话。（A）

反例是键盘输入：候选栏不为 50ms 的等待显示任何加载态。这不是遗漏，而是判断——键盘的可接受等待远短于语音，给 50ms 加骨架屏只会制造闪烁。**该安静的地方安静，该解释的地方解释**。（C，按默认值与交互形态推断）

## 3. 可发现性

豆包自己认定的能力目录写在工具栏里。`n7/r.java` 与 `el/f.java` 给出的按钮池是：语音条（`btn_speech_bar_two` / `_single`）、剪切板、智能整理、翻译、表情、常用语、手写检索、选择面板、繁简、单手、移动光标、键盘调节、发送、收起（对应 `btn_toolbar_*` 与 `btn_hide`）。（A，代码；中文名按资源语义对应，B）

截图里首屏可见的是四到五个图标加一个收起箭头，其余藏在工具栏入口后面。真正"没人提醒就不会发现"的是这些：

- **上滑输符号**。`fusiyin_enable_title`「上滑输入数字符号」默认关；开着时 C 上滑出 `#`。这条能力只在长按浮层里顺带露出来——三格里摆着 `C / # / c`，但没有一句话说"上滑"。（A，默认值；A，截图；A，`ACCEPTANCE.md` 第 14 项）
- **长按浮层**。按住字母键，行内展开成三格（大写 / 字符 / 小写），没有文字标签，唯一发现路径是"手一直不抬"。（A，截图中 C 键位置的三格形态）
- **单手、移动光标、手写检索、繁简、翻译**。都在工具栏里，且要先点开工具栏入口才看得到全部。（B，代码；A，截图中工具栏为图标行）
- **语音口令**。埋在"语音转文字"二级页，副标题才解释「通过说出指定词语来执行操作」。（A）

对模块的启示很直接：**豆包每一个隐藏手势都配了视觉回执**——上滑有长按浮层里的符号格预告，长按有三格浮层，语音有条形动画，候选有就地替换。模块的"下滑"是这套系统里唯一没有预告的手势：长按 C 时浮层只摆出 `C / # / c`，不教"往下滑会复制"，用户第一次尝试只能靠 README。（A，截图 + 模块 README；C，对"唯一"的判断基于现有截图）

另外，工具栏按钮的 `contentDescription` 直接用了资源键名（`CandidateIdleView.java` 的 `setContentDescription(str)`，`str` 形如 `btn_toolbar_send`），读屏会念出英文键名。这是豆包自己的可发现性缺陷，也说明"能力目录"这一层他们没做完。（B）

## 4. 模块与原生行为的不一致

| 机制 | 原生 | 模块 | 用户能否感知 | 等级 |
|---|---|---|---|---|
| 被映射键的 DOWN | 立即交给引擎 | 扣住，300ms 后归还 | 浮层约晚 300ms | A（时序）/ C（感知） |
| 按下反馈 | 气泡随 DOWN 出现 | 气泡随归还出现 | 被映射键"慢半拍" | A（机制）/ C（感知） |
| 12–60px 死区 | 无此区间 | 不打字、不触发、无反馈 | 强感知，"按键失灵" | A（行为）/ C（判断） |
| 触发反馈 | 无此动作 | `KEYBOARD_TAP` 且 `FLAG_IGNORE_VIEW_SETTING` | 关震动仍会振 | A |
| 长按浮层 | 500ms | 归还后重算，实测更晚 | 跨键对比才容易察觉 | A（模块文档）/ C（感知） |

### 4.1 300ms 归还：代价在哪里

`GestureGate.HAND_BACK_MS = 300`。未映射键的长按浮层在按下约 500ms 后出现；映射键的引擎在 300ms 才第一次看到 DOWN，浮层整体后移。`ACCEPTANCE.md` 与 `doc/01` 记的是"弹框因此比未映射键晚约 300ms"（A）。同一排键里，B 长按 0.5 秒出三格，C 长按 0.5 秒什么都不出——**用户不会归因到"这个键被模块接管了"，只会归因到"这个键坏了"**。（C）

更麻烦的是中间那段：按住 400–600ms 松手，既没到浮层显示点，也没滑过 60px，结果一个字母都不出、一次振动都没有。这段"静默窗口"是当前设计里最像 bug 的部分。（C，按 300ms 归还 + 500ms 长按 + 60px 触发线推得，未实测该区间的用户结果）

### 4.2 死区：最容易被当成故障

12px 的门槛低于很多人的点击纵向抖动；越过 12px 又没到 60px 就判 DEAD，不补发、不触发、不发振动，交付构建 `DEBUG=false` 时连日志都没有。（A，`GestureGate.onUp` 与 `Config.DEFAULT_DEBUG`）用户看到的是"我按了 C，没反应"。（C）

### 4.3 触感绕过了用户的开关

`Actions.haptic` 用 `KEYBOARD_TAP` 加 `FLAG_IGNORE_VIEW_SETTING`，不读豆包的 `enable_key_vibrate`（默认关），也不读系统触感开关。（A）在会议、静音场景里用户关掉了按键震动，模块仍然振——这是"应用不尊重设置"的强信号，比延迟更容易被记住。（C）

### 4.4 可执行的改进建议

**建议 1：死区从"静默吞掉"改成"可感知的拒绝"，门槛提到 24px**

- 改什么：`GATE_FRAC` 从 12/909 提到约 24/909；24–60px 仍判 DEAD，但 DEAD 时发一次与 FIRE 可区分的触感（两次短振对一次 `KEYBOARD_TAP`），设置页加"手势提示"开关，默认开。
- 为什么：12px 容不下正常点击抖动，而 DEAD 目前零输出；先让"没触发"和"没按上"在触觉上分开，再谈用户教育。
- 怎么验证：同一按键横扫 0/6/12/18/24/36/48/60/72px，每档 20 次，记录输出类别；验收线是 ≤24px 全部出字、>60px 全部 FIRE、24–60px 全部有可区分触感且无字符泄漏。再让 3 人各盲点 20 次，统计"以为没按上"的次数，目标 0。

**建议 2：归还阈值自适应，把浮层延迟压到 150ms 以内**

- 改什么：`HAND_BACK_MS` 从 300 降到约 150（推导：引擎长按 500ms，减去实测浮层相对 DOWN 的 350–450ms 延迟，留 50ms 余量），只在"当前键存在长按备选"时启用；设置页加"长按优先 / 快捷键优先"两档，后者维持 300ms。
- 为什么：同一排键出现两种长按延迟，是当前最容易被误判为故障的差异；150ms 已在人眼可辨阈值附近，普通下滑通常在 200ms 内越过 60px，仍有安全余量。
- 怎么验证：复用 `doc/01` 的截屏差分折线，同一构建、同一脚本分别长按 C 与 B，测浮层出现帧的时间差，要求 ≤150ms；同时回归 20 次下滑、上滑、轻点，确认无误触发、无字母残留、长按后仍可触发快捷键（`ACCEPTANCE.md` 第 27–28 项同款判据）。

**建议 3：触感遵循豆包与系统的开关，并区分三类事件**

- 改什么：FIRE 前读豆包的 `enable_key_vibrate`（`SettingsConfigNext`，键名即字符串）与系统 `HAPTIC_FEEDBACK_ENABLED`，任一为关则不振动；开启时 FIRE 用比普通按键更重的一档，DEAD 用另一档（见建议 1）。
- 为什么：豆包默认关闭按键震动，模块无条件振动，等于绕过用户明确做过的选择；三类事件共用一个触感也浪费了唯一的非视觉反馈通道。
- 怎么验证：2×2 矩阵（豆包震动开/关 × 系统触感开/关）各下滑 5 次，记录是否振动；验收线是与同排未映射键的振动行为完全一致，静音模式下 0 次振动。

**建议 4：把"第一次落到死区"当成一次教学机会**

- 改什么：检测到本机第一次 DEAD 时（仅一次，持久化标记），用 `Toast` 说一句可执行的话，例如"往下滑过键盘高度的一半再松手，才会触发"；同时把设置页副标题从"按住字母下滑，执行复制、粘贴、剪切、全选、撤销。"扩展成可照做的动作说明。
- 为什么：豆包所有隐藏手势都有视觉预告，模块一个都没有；死区正是新用户第一次尝试最可能落到的区间，那里现在什么都不发生。
- 怎么验证：清数据后第一次 30px 下滑，Toast 出现且只出现一次，第二次不再出现；连续正常打字 100 次无 Toast；`dumpsys package` 组件数不增加（守住 `ACCEPTANCE.md` 第 41 项）。

**认账：不建议做的**

- 不往键盘上叠自绘提示（箭头、轨迹线）。豆包键盘是 native 自绘位图，叠 View 会和候选栏、浮层的层级打架，每次版面变化都要重新标定，收益只是"好看"。放弃。
- 不把 DEAD 改成"补发成轻点"。那会把"手抖下滑"变回"打出字母"，用误输入换反馈，与死区存在的理由冲突。放弃。

## 5. 文案

1. **「静音状态无法开启按键声音」**（`sound_switch_disable_toast_title`，A）先说阻塞原因再说结果，没有"请"字堆叠，也没有把责任推给用户。差在没给下一步——系统静音时用户往往不知道自己静音了，补一句"请关闭静音模式"更完整。
2. **「语音处理中，请稍等」**（`asr_in_work_tip`，A）承认等待存在，不假装瞬时。差在"请稍等"没有边界：超过三秒就不再提供信息，用户开始怀疑卡死；可参照同包的「识别优化中」，至少指出在做什么。
3. **「无线网络弱，已切换移动网络优化识别」**（`asr_switch_cell_setting_guide_text`，A）整套文案里最好的一条：原因、已执行的动作、目的一句话说完，还主动交代了用户看不见、又与流量和隐私相关的行为，没有"为了提供更好的服务"这类空话。
4. **「表达清晰，无需整理」**（`smart_organize_text_unchanged_toast`，A）把一个"没有结果"的操作写成判断，而不是"整理失败"。缺点是替用户评价了表达，敏感场景可能被读成冒犯；"当前内容无需调整"更中性。
5. **「请确保系统设置中「声音与触感」-&gt;「系统触感」为开启状态」**（`key_vibrate_system_haptic_tip`，A）差。路径写死成 iOS 风格的"声音与触感 → 系统触感"，Android 上没有同名菜单，各 OEM 也不同；`-&gt;` 还是未转义的代码痕迹。这是把内部字符串直接丢给用户，和前面几条的水准不在一条线上。

横向看：豆包在**状态**上写得细（听、识别、处理、整理、提交各有词），在**路径**上写得糙（设置路径、权限路径都写死）。前者值得抄，后者不要抄。模块设置页已有"状态句在前、诊断在后"的结构（`SettingsActivity`），方向对；要补的是把"读不到"翻译成用户能做的动作，而不只是陈述事实。（A，模块源码；C，评价）
