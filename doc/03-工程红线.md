# 工程红线

裁剪自 `~/SEC/tstools/CLAUDE.md`，只保留与本仓相关的部分。按**炸伤程度**排序。

`CLAUDE.md` 里只留 P0 摘要，完整清单以本文件为准。

## P0 — 不许碰

- 密码 / token / 授权码硬编码，或写进日志与对话记录。
- 把未经校验的外部输入直接交给解析器或反射（本仓对应：`Method.invoke` 前不判空、
  不校验目标与参数类型）。
- 空 `catch` 静默吞异常（Java 里的 `except: pass`）。至少 `Log.e` 一行。
  本仓的收敛写法是 `Log.once(key, msg)`：预期内、会反复发生的失败（服务未绑定、
  设备不支持触感）用 once，真异常用 `Log.e`（消息一行 + `XposedBridge.log(t)` 堆栈）。
- 大文件全量 `.read()` / 一次 `readBytes()`。

## P1 — 不炸但让人烦

循环里做 I/O；网络请求无 timeout；文件句柄不用 try-with-resources；
用异常兜业务分支并打堆栈。

## P2 — 规范

命名混乱、嵌套 ≥ 3 层、硬编码数字 / URL；注释写"这段代码做什么"而不是"为什么这样做"。

## 例外必须认账

允许打破，但必须写注释说明原因：`// 性能原因` / `// TODO 上线前删除` / `// 平台约束` /
`// 历史遗留`。没有注释的破例就是偷懒。

## Spike 规则

不确定性高的想法（库能不能用、接口是否可达、格式能否解析）先做最小可丢弃实现，
文件名或目录带 `spike_` 前缀，免检上述红线，两小时出结果，不考虑分发与打磨。

**spike 代码不允许直接转正。** 验证通过后，生产实现重写或按全量标准过一遍。
"能跑的验证脚本"和"生产工具"是两种东西——差的那部分工作量（错误处理、日志、边界）
正是红线存在的原因。

本仓的实例：长按浮层的两轮 spike 用 `// SPIKE:` 注释就地改、测完立刻还原；
不还原的后果是 `param.setResult(null)` 被注释掉而没人发现。
