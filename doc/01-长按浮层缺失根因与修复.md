# 豆包输入法长按浮层缺失：根因定位与修复报告

日期：2026-10-26
范围：`app.xuan.doubaoslide`（LSPosed 模块，作用域 `com.bytedance.android.doubaoime`）

## 一、问题陈述

用户报告：**其他字母长按会弹出「大写 / 字符 / 小写」浮层，被映射的 C、V 长按没反应。**

被映射的键是 C V X A Z 五个，分别绑定复制、粘贴、剪切、全选、撤销。

用户还追加了一条要求：**长按之后这一下仍要能当快捷键用**（"我不可以继续当快捷键用吗？"）。
这一条决定了修复不能是"放弃快捷键换浮层"。

## 二、最初的假设（错的）

第一版诊断的结论是：

> 弹框由引擎的 native 长按计时器驱动。模块扣住了 DOWN，引擎没收到 DOWN，计时器就不会启动。

据此写下的实现是"**长按归还**"：按住一段时间仍没下滑时，把这次按下补发给引擎，
让它的计时器跑起来；抬手时若滑过触发线就触发快捷键并发 `CANCEL` 撤回预编辑。

实现本身写完了（`GestureGate` 加 `HANDBACK` 判定 + `SlideHook` 加归还定时器与
`revokeComposition`），单元测试 36 项全绿。**但真机上浮层并没有出现。**

## 三、真正的根因

### 3.1 测量通道先修好

浮层是 native 自绘的：`uiautomator dump` 的视图树里没有它，它也不产生任何日志。
纯文本拿不到，只能从截屏取。

这里踩了两个坑，都记在 `CLAUDE.md` 的「调试规范」里：

1. **裁剪窗口必须跟着被按的键走。** 浮层出现在**被按键的正上方**（键上方 77–227px），
   不是固定在候选栏。最初把窗口固定在 `t` 的位置，于是 `c` 的浮层被裁在窗外，
   得出"完全没有浮层"的错误结论。
2. **要比对形态，不要比像素计数。** 浮层里画着字母，`b` 和 `c` 的笔画数不同，
   同一个浮层的"变化像素数"会差一截（实测 `b` n=7~15，`c` n=1~5）。
   按计数判"在不在"会得出假阴性。

修好通道后的判据：把该键正上方 `y-230 … y-70` 区域与基准帧做
`blend=all_mode=difference` 差分，打印 ASCII 折线，比对**形状**。

### 3.2 四组对照

固定同一构建、同一脚本、同一位置，只换一个键：

| 条件 | 映射键 C 的浮层形态 |
|---|---|
| 未映射键 B（对照） | 完整三格 |
| 模块完全放行（不碰任何事件） | 完整三格 |
| 模块扣住 DOWN | 无（只剩中间一个组合预览气泡） |
| 模块 300ms 后补发 DOWN | 残缺 |

「完全放行」和「扣住 DOWN」之间的差集落在 **y1800–1930**，正是浮层所在。

### 3.3 决定性的一步：看引擎的调用链

`KeyboardView` 有一组可 hook 的方法。对同一位置、一次长按，比较映射键与未映射键的调用序列：

```
未映射键 B                          映射键 C
─────────────────────────────────────────────────────────
onTouchEvent(ACTION_DOWN)          onTouchEvent(ACTION_DOWN)
preHandleTouchEvent(ACTION_DOWN)   preHandleTouchEvent(ACTION_DOWN)
delaySendLongPressMessage(x, y)    delaySendLongPressMessage(x, y)
nativeTouch(h, x, y, 0, t)         nativeTouch(h, x, y, 0, t)      ← 模块补发的
drawTouchTipBubbleShadow(...)      drawTouchTipBubbleShadow(...)
drawTouchTipBubble(...)            drawTouchTipBubble(...)        ← 第一次
                                   nativeTouch(h, x, y, -1, t)     ← 引擎 501ms 发 LEAVE，模块吞了
nativeTouch(h, x, y, -1, t)        drawTouchTipBubbleShadow(...)
drawTouchTipBubbleShadow(...)      drawTouchTipBubble(...)        ← 第二次
drawTouchTipBubble(...)            ← 缺这一格
nativeTouch(h, x, y, 1, t)
```

**Java 层完全一样**：两个键都调了 `delaySendLongPressMessage`（长按计时器是 Java 层的
Handler 消息，不是 native 的）。差异只在 native 侧：

- 引擎在按住 501ms 后发 `nativeTouch(-1)`（LEAVE）。
- **收到这条 LEAVE，引擎才画第二个气泡**（大写 / 字符 / 小写那三格）。
- 模块的 `dispatch` 在末尾无条件 `param.setResult(null)`，把 LEAVE 吞了。

所以浮层画出来需要引擎同时看到两样东西：

1. 一次 `nativeTouch(0)`（DOWN）——决定"有这根手指"；
2. 一次 `nativeTouch(-1)`（LEAVE）——决定"到点画浮层了"。

模块两样都拦，浮层就残缺。

**第一版诊断错在**：把"浮层不出现"归因于"native 长按计时器没启动"，而计时器其实在
Java 层（`delaySendLongPressMessage`），两个键都调用了它。真正的开关是 LEAVE。
补发 DOWN 之所以只画出残缺的一角，就是因为补发之后再没有 LEAVE 走到引擎。

## 四、修复

### 4.1 改动

| 位置 | 改动 |
|---|---|
| `GestureGate` | 新增 `Verdict.HANDBACK` 与 `onHandback()`：按住够久又没滑过触发线时，把这一次按下归还给引擎。归还后仍扣住事件（判定还欠一个 UP） |
| `SlideHook` | `scheduleHandBack()`：DOWN 时用 `View.postDelayed` 预约归还（300ms）。手指不动时引擎不发任何事件，"按住够久"这件事只能在 DOWN 时预约 |
| `SlideHook` | `handBack()`：用反射把这次 DOWN 连同**原始时间戳**补发给引擎 |
| `SlideHook` | 归还后**放行 LEAVE**（原来是吞掉）——这是浮层能画全的关键 |
| `SlideHook` | `revokeComposition()`：触发快捷键或明确作废时发一条 `CANCEL`（`action=3`），撤回引擎组合区里那个字母 |
| `SlideHook` | `finish()`：归还过的手势，抬手时只补发后半段（DOWN 引擎已经有了） |

`CANCEL` 语义是实测确定的：

- 引擎收到 `CANCEL` 会把预编辑缓冲整个撤掉，长按浮层一起收起；
- `CANCEL` **不**影响已存在的组合（"g" 的组合还在）；
- **只有"引擎只见过 DOWN"时 `CANCEL` 才干净**——一旦引擎见过 MOVE 再收 `CANCEL`，
  候选栏不会回到空白。

所以归还之后 MOVE 一律扣住不转发：引擎看不到滑动过程，也就看不到"这是往下滑"
而不是"这是长按"。

### 4.2 真机验证

全部在小米 14 Pro / Android 16 / 豆包输入法双拼 26 键上实测，证据等级 A。

| # | 项 | 实测 | 证据 |
|---|---|---|---|
| 26 | 长按浮层（映射键 C） | 键正上方出现与未映射键 B **形状逐行一致**的三格浮层 | 截屏差分折线 |
| 27 | 慢速下滑不静默失效 | 按住 0.7s 后下滑 94px → `手势 c -> copy ok=true dy=94 (fire>60) 归还后触发` | modules.log |
| 28 | 长按后仍可下滑触发 | 同上，`归还后触发` 出现在日志里 | modules.log |
| 29 | 触发后不残留字母 | 触发 copy 后标题字段仍是 ` `（基线），没有 `c` | `uiautomator dump` |
| 30 | 死区（归还后） | 按住 0.9s 后下滑 25px → `手势作废：dy=25 在 12 与 60 之间` + `撤回预编辑：c（CANCEL）` | modules.log |
| 31 | 长按浮层选中项一致 | 映射键 C 长按后提交 → `# `；未映射键 B 长按后提交 → `？ ` | `uiautomator dump` |
| 32 | 未映射键不受影响 | 按住 B 0.9s：日志只有 `DOWN 648,625 字母=b`，无 `扣住`/`长按归还` | modules.log |

**顺带修掉的既有缺陷**：>500ms 的手势原本被 LEAVE 吞掉，判定状态在 `dispatch` 里被
`GESTURE.reset()` 清空，抬手时判成"不是我们扣下的手势"→ 原样放行成一次无主的 UP →
**什么也不发生**。用户报告"按住 0.6s 后下滑没有任何输出"就是这个。现在 LEAVE 在
归还后被放行，判定状态保留，慢速下滑正常触发。

## 五、代价

1. **归还后引擎的组合区里会多出这个字母。** 触发快捷键时发 `CANCEL` 撤掉。
   代价是引擎收到的是"按住了 300ms 才被告知有这根手指"，浮层因此比未映射键晚约 300ms。
   这是"既要浮层又要快捷键"必须付的价。
2. **死区仍然吞按键。** 12px–60px 之间既不打字也不触发。拿"手抖误触"换"不误触发快捷键"。
3. **多指仍然不触发快捷键。** 见到第二根手指（`action=5`）就放弃判定、只做补发。
   引擎在 `MOVE` 里不带指针下标，`handle` 在多指事件里也是同一个值，分不清坐标归属。
   去掉这条限制时 A + C 两指实测误触发过一次 `selectAll`。

## 六、复盘：这次为什么会绕远

三条可复用的教训：

1. **"扣住 X 导致 Y 不出现"这类推断，必须先确认 X 是 Y 的唯一开关。**
   这次的错误推断是"扣住 DOWN ⇒ native 长按计时器不启动"。实际计时器在 Java 层
   （`delaySendLongPressMessage`），两个键都调用了它；真正的开关是引擎的 LEAVE。
   查证方式是 hook 引擎的方法打调用序列——比读字节码快，比猜快得多。

2. **测量通道本身要先验证，再拿来下结论。**
   本次有两次结论（"完全没有浮层"、"spike 有缺陷"）纯粹是裁剪窗口选错造成的。
   裁剪窗口错位时，测到的可能是组合预览气泡、候选栏文字或按键高亮。
   **通道的判据必须先用已知正反例校准**（未映射键 = 阳性对照，已知无浮层的场景 = 阴性对照），
   再去测未知。

3. **像素计数不能当形态判据。** 浮层内容不同 → 计数不同 → 假阴性。要比形状。

## 八、开放问题

1. **`HAND_BACK_MS = 300ms` 是拍的。** 依据是"普通下滑从按下到越过 60px 通常不到 200ms，
   300ms 留了余量"，没有做过分布测量。慢速下滑的用户（手指移动慢）可能在 300ms 内
   滑过 60px 之前就触发归还，引擎会短暂看到一次 DOWN 再被 CANCEL 撤掉。
   可考虑按位移趋势自适应，但需要先测真实下滑的耗时分布。
2. **归还的 DOWN 带原始时间戳。** 引擎据此认为这一下已经按了很久。实际效果是浮层
   在归还后立刻开始画，而未映射键要等 501ms 的 LEAVE。两者时机不同但结果一致，
   机制没查清。
3. **多指的现场复测没做成。** `input motionevent` 是单指序列，注不出真多指
   （系统把第一指转成了 CANCEL）。多指限制仍由 `onHandback()` 的
   `multiPointer` 分支保证，但真机多指路径这次没有独立复测。
