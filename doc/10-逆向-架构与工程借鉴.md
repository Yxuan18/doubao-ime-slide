# 逆向：架构与工程借鉴

目标不是复刻豆包输入法：从 179 MB、3.8 万个类里挑出**能搬进小项目的结构决策**，并标出哪些是体量带来的包袱。评判标准只有一条——一个人能不能长期维护得动。

**材料与方法**

- 体积：`unzip -lv /tmp/doubao-ime/apk/base.apk`（同时取压缩与未压缩两列）
- 原生库：`nm -D --defined-only`、`strings`、手写 ELF `.dynamic` 解析取 DT_NEEDED
- 类/方法计数：`dexdump -f`（各 dex 头）、`dexdump -d`（反汇编 `ImeService.onCreate`）
- 源码：jadx 1.5.1 输出（`/tmp/doubao-ime/src/sources`）
- 证据等级：**A** = 实测输出或直接读到的代码事实；**B** = 反编译可见但未运行验证；**C** = 推断，写明依据

## 0. 先更正三个流传的前提

1. **KeyboardJni 不是「618 个 static native」。**【A】`KeyboardJni.java` 里 `native` 声明 **217 个**，全部是实例方法；`jni_methods.log` 的 `COUNT 618` 是 Frida 枚举到的**全部**方法，包含 Java 包装层（例如 `private static String ExecutePost(...)`、`ExecuteQUICPost(...)` 都是普通 Java 方法）。514 个唯一方法名中，60 个仍是单/双字母混淆名。
2. **四个 .so 合计 7.1 MiB 只是核心层，不是 native 总量。**【A】`lib/arm64-v8a` 实际有 **93 个 .so**，解压合计 **85,661,832 B**（占 APK 未压缩体积 25.06%）；最初提到的那四支只占 **7,464,216 B**。
3. **文件名会骗人：`libkeyboard.so` 不是引擎。**【A】`libshell.so`（8,878,856 B）导出 `oime_engine::` 与 `shell::InputState`（`HandleInput`/`MatchKey`/`Pinyin9Mode`/`ShuangPinScheme`/`WubiScheme`），`libkeyboard.so` 的 DT_NEEDED 里第一项就是 `libshell.so`。真正的输入法内核在 `libshell`，`libkeyboard` 是键盘界面与业务控制器。

## 1. Java 与 native 的分工

### 1.1 五个核心库各自干什么（A：DT_NEEDED + 导出符号 + 字符串里的源文件路径）

| 文件 | 大小(解压) | DT_NEEDED | 职责（证据） |
|---|---|---|---|
| `libshell.so` | 8,878,856 | `libtrack, liboime-config, libandroid, liblog, libm, libdl, libc` | **输入法内核**：`oime_engine::`、`shell::InputState`、`Pinyin9Mode`/`Pinyin26Mode`、`ShuangPinScheme`、`WubiScheme`、`ConvertUtils`；字符串含 `third_party/marisa-0.2.6`、`protobuf-v3.21.12` |
| `libkeyboard.so` | 5,081,136 | `libshell, libime_ui_android_platform, libz, libcurl, libtrack, liboime-config, liblog, libandroid` 等 11 项 | **键盘 UI + 业务控制器**：源文件路径含 `src/keyboard/src/{ui,controller,cloud,llm,translate,correction,track,perf,jni}`；导出 75 个 `ui::` 类、38 个 `keyboard::` 类、54 个 `GetInterface` 工厂 |
| `libime_ui_android_platform.so` | 722,400 | 仅 `libandroid, libdl, libc` | **平台后端**：12 个导出，`GetFont/GetImage/GetTimer/GetWindow/GetAssets` + `CreateView/nativeDraw/calcTextSize/drawLinerGradientText/drawTouchTipBubble`——把原生 UI 的绘制指令翻译成 Java `Canvas` 调用 |
| `librelax.so` + `librelaxui.so` | 1,527,536 + 133,144 | `liblynxbase, libc++_shared`（`librelax` 另需 `librvm`） | **JS 运行时**：导出 `RTS__1_1*`（animationFrame / bridge / console / navigation），符号来自 `lynx::lepus`，即 Lynx 系脚本引擎；`librelaxui` 只暴露 `RelaxInitUIPropertyValueFactory`/`RelaxGetUIPropertyValueFactory` |

`librelax` 依赖的 `librvm.so` **不在 APK 里**（【A】`unzip -l | grep librvm` 无结果），推测运行时按需下发（【C】，依据：Relax 的 `LibraryLoader` 是异步按名加载，见 `el/l.java`）。另外 `libshell` 的 DT_NEEDED 里也带着 `libtrack`（埋点）和 `liboime-config`（配置），说明引擎层把「上报」和「读配置」当成了硬依赖，而不是可选回调——这两条依赖在小项目里应该是接口注入，不该编进内核。

### 1.2 分界线画在哪

**下沉到 native 的（A/B）**：拼音/双拼/五笔的转换与候选、用户词库读写、云词库同步、剪贴板历史、LLM 候选状态（`UpdateLLMCand`/`SelectLLMCand`/`CompChangeToRequestLLM`）、翻译模型（`translate_model.cpp`）、键盘布局与命中测试（`ui::Pinyin9Layout`、`ui::ButtonChar`）、点击埋点（`track::Track::PostEvent`）、配置缓存（`liboime-config` 的 `config::ImeKv`）。

**留在 Java 的（A/B）**：IME 生命周期与 `InputConnection`、语音采集（`AsrManager.java` 2,635 行，走 `AudioRecord`/`AudioFocus`）、LLM 传输（`LLMRequest.java` 444 行）、账号/设置页/弹窗/皮肤资源加载、Lottie 播放、推送、升级。

**关键接口方向是双向的**：native 通过 upcall 调 Java 做网络——`ImeEngineHostNetworkBridge`（`@Keep`，4 个 native）与 `KeyboardJni.ExecuteQUICPost(String,String,int)` 都是 Java 实现【A：方法体】；`libkeyboard.so` 的字符串里有 `keyboard/src/jni/android_host_network_bridge.cpp`【A】，说明 native 侧存在对应的回调入口，但谁在何时调用它未在运行时验证【B】。可确认的是：引擎侧同时存在 `libcurl`（DT_NEEDED）与 Java 侧 QUIC，两条网络路径并存。

**对一个单人项目该怎么借鉴**：只把「每帧都跑」和「将来可能换平台」的两类逻辑放进 native。布局与命中测试每帧跑，值得；账号、设置、网络不值得。反过来，网络与系统 API 一定留在 Java——native 里那份 `libcurl` 让 `libkeyboard.so` 多了一条依赖链（`libcurl.so` 5,348,152 B），却仍有一部分逻辑绕回 Java 走 QUIC，等于两套并存。

## 2. 混淆与可维护性

### 2.1 实测分布

- 【A】4 个 dex 共 **37,929 个 class_defs**、**210,717 个 method_ids**（`dexdump -f` 四份求和）；jadx 落成 **23,419 个 .java**。
- 【A】`com/**` 10,182 个类；`androidx/**` 2,337 个；**1,765 个混淆顶层包**（绝大多数是 `a/`、`a0/`、`bf0/`、`o40/` 这样的 1–2 字符目录）装下约 10,400 个类。
- 【A】语义包内部也在混淆：`com.bytedance.android.input`（768 个类）里 **403 个类名是 1–2 字符**（52%）；`doubaoime` 包 321 个类中 99 个（31%）。子包差异很大：`keyboard/areacontrol` 52 个类里 49 个混淆，而 `keyboard/emoji`、`keyboard/word_segmentation`、`keyboard/component` 全保留语义名。

### 2.2 策略读法

保留下来的名字有一个共同点：**被 Java 之外的什么东西引用**。manifest 里的组件、XML 布局里的自定义 View（`ImeListItemView` 80 次、`ImeTitleBar` 34 次）、JNI upcall 目标（`KeyboardView`、`ImeEngineHostNetworkBridge`）、`@Keep`、以及跨模块的 api 接口。反过来，只在内部调用的实现类哪怕在语义包里也被压成单字母。

**借鉴**：给自己的项目划一条「契约面」，只保住这条线上的名字：

- 保住：manifest 组件、XML 里出现的 View 全名、JNI/反射入口、序列化字段名、跨模块 api 包。
- 放开：实现类、内部 DTO、只在同模块调用的工具。R8 默认就能做，关键是别为了「好看」把整包 `-keep`。
- 反例警告：`input` 包 52% 的类名不可读，意味着**线上崩溃栈里一半的帧只能靠行号定位**。单人维护没有专门的值班同学帮忙翻译，代价比大厂高。建议至少对 `input` 这类核心包开 `-keepnames`（保住类名、仍可压缩/优化）。

## 3. 启动与注入路径

### 3.1 两段初始化（A：源码 + 反汇编）

`ImeApplication.attachBaseContext` 的顺序（`ImeApplication.java` 直接可读）：

1. 多进程 WebView 数据目录后缀（`WebView.setDataDirectorySuffix`）
2. `IAppGlobals.e()` 全局上下文
3. `tf.a()` 注入（`[ime-thread]-init` 打点，带 try/catch 降级）
4. `ImeKv.init(this)` 键值存储
5. `IEnvironment.isReady()`、`InitScheduler.config(TaskConfig…)`
6. **字体预热丢到后台线程**（`qihei` / `misans_*`，`StartupSpeedExperiment` 开关控制）
7. `InitScheduler.onPeriodStart/End(APP_ATTACHBASE2SUPER)`、`(APP_SUPER2ATTACHBASEEND)`

`ImeService.onCreate` 的顺序（`dexdump -d` 反汇编，1,733 个 16-bit code units）：

1. `super.onCreate` → 打点 `service_super`
2. `SelectionTracker` + `InputConnectionWrapper`
3. `KeyboardJni.SetImeService(this)` → `getKeyboardJni()`（**类加载即 `System.loadLibrary("keyboard")`**，常量名 `SETTINGS_SOURCE_KEYBOARD`）
4. `IEnvironment.isReady()`
5. 建 `KeyboardView`、`setIdName/setBackgroundColor/setListener`
6. **`KeyboardJni.initKeyboard(10 个 String + 3 个 boolean)`** —— 引擎在这里才真正启动
7. `upgradeCommonPhraseDict`、`loadAsrModifyPairDict`
8. 设置监听、引导配置、剪贴板监听、广播接收器，最后 `post` 一批延迟任务

`KeyboardJni` 的静态块依次 `loadLibrary("ime_ui_android_platform")` → `loadLibrary("keyboard")` → `ImeKvJniBridge.initialize()` → `loadLibrary("track")`，每一步都单独 catch `UnsatisfiedLinkError`【A】。

### 3.2 懒加载在哪一层

- **布局层**：`assets/skin/default/input_main.xml` 里写着——「启动速度优化：键盘分帧绘制：主布局只保留空容器，当前键盘按需创建，其余键盘在首帧后逐帧补齐，避免启动时一次性解析全部键盘 XML」【A，资源原文】。这是最值得抄的一条。
- **服务层**：`IEnvironment`/`IInputSettings` 是「接口 + 懒持有 + 注册表」——`pt0.k<T>` 是一个 `volatile` 双检的 Lazy，`IEnvironment.a` 内部 `e.a.f49177a.a(IEnvironment.class)` 首次访问时才解析实现，取不到直接抛 `IllegalStateException("app module must have an implementation of this service！")`【A】。
- **任务层**：`com.bytedance.lego.init.InitScheduler` 把初始化切成 13 个 `InitPeriod` 枚举值（12 个真实周期 + `NONE`，从 `APP_ATTACHBASE2SUPER` 到 `MAIN_ONRESUME2SUPER`）+ 空闲任务（`IdleTaskConfig`，默认超时 8,000 ms）【A】。

**借鉴（按性价比排序）**：① 分帧建视图——首帧只建当前键盘，其余 `post` 到下一帧；② 用「接口 + Lazy 单例 + 注册表」替代 Application 里一长串 init；③ 字体/模型预热放后台并允许失败回退。不要照搬 13 个生命周期钩子：这套框架的价值在几十个 SDK 排队时，单项目里就是过度设计。

## 4. 多媒体与运营基础设施

| 组件 | 解决什么（证据） | 独立开发者的廉价替代 |
|---|---|---|
| **bytehook** | native inline hook 库：`libbytehook.so` 59,016 B，Java 侧只有 1 个类【A 存在性】；具体 hook 了哪些目标未查【C】 | 不用。本仓已经用 LSPosed 在 Java 层 hook；单人项目优先 Java 反射/官方 API |
| **keva** | 轻量 KV：`libkeva.so` 412,576 B + 10 个 Java 类【A】；native 侧另有 `config::ImeKv`（`liboime-config.so`，导出 `GetValue/AddObserver`）【A】，两者是否同一份数据未证实【C】 | `SharedPreferences`（小）或 `DataStore`（要异步/类型安全时）。别自造 |
| **geckox** | 资源包增量更新（`libgeckox_bspatch.so` + 34 个类）【B：由类名与 bspatch 符号推断】 | assets + 一个版本号字段；真需要热更再上 Play Asset Delivery / 自建 CDN |
| **ttnet / QUIC** | `com/ttnet` 166 类 + `libsscronet.so` 6,359,392 B + `libttboringssl.so`；QUIC 相关还有 `ImeNetSDK`（8 个 native）+ `libime_net_sdk.so` 6,854,928 B【A 存在性；调用关系为 B】 | OkHttp。HTTP/2 对输入法的「按字请求候选」已经够；QUIC 的弱网收益要海量请求才摊得平 |
| **lynx / relax** | 跨端脚本 UI：`com/lynx` 736 类 + `com/bytedance/lynx` 182 类 + `liblynx.so` 4,718,880 B；Relax 另加 431 类【A 存在性；用途为 B】 | 原生 View，或 WebView + 本地 HTML。要模板化活动页，JSON → 手写 View 映射就够 |
| **apm / applog / crash** | 监控、埋点、崩溃：83 + 34 + 155 个类，native 侧 15 个 `libnpth_*.so`（最大 222,368 B）、`libmonitorcollector-lib.so` 313,744 B【A 存在性】 | Sentry / Firebase Crashlytics + 一张自建事件表。native 崩溃聚合单人维护不起 |

**判断标准**：这些组件全部是「多业务线共用一套 SDK」的产物。单人项目的对应物是「一个库 + 一个云服务」，不是「一套框架」。keva 这类**薄封装**可以借鉴思路（一个 KV 接口，两边实现），ttnet/lynx 这类**厚平台**直接跳过。

## 5. 体积：179 MB 花在哪（全部实测）

APK 179,389,745 B（171 MiB），解压后 341,759,784 B，3,375 个条目。按压缩体积排：

| 目录 | 压缩后 | 占 APK | 解压后 | 里面是什么 |
|---|---:|---:|---:|---|
| `assets/dict/` | 89,619,953 | **49.96%** | 175,932,673 | 词库/模型 |
| `lib/arm64-v8a/` | 35,045,156 | **19.54%** | 85,661,832 | 93 个 .so |
| `res/` | 32,968,020 | **18.38%** | 37,678,981 | 字体 + 图片 |
| 根目录（dex + arsc） | 16,398,149 | **9.14%** | 34,956,267 | 4 个 dex + `resources.arsc` |
| `assets/lottie/` | 2,395,634 | 1.34% | 3,741,603 | 43 个动画 |
| `assets/skin/` | 1,018,729 | 0.57% | 1,182,063 | 键盘 XML + 皮肤图 |
| `assets/mlkit_barcode_models/` | 880,888 | 0.49% | 880,888 | 扫码模型（STORED） |

**dex**：4 个文件解压 31,621,608 B（9.25% of 解压总量），压缩后 13,141,248 B（**7.33% of APK**）。逐个：9,858,672 / 10,185,204 / 9,137,628 / 2,440,104。

**native 的 35 MB 里，输入法自己的库只占 6.85 MB（3.82%）**：
- 自家 7 支（`libshell`、`libkeyboard`、`librelax`、`librelaxui`、`libtrack`、`liboime-config`、`libime_ui_android_platform`）：解压 17,632,984 B、压缩 **6,851,927 B（3.82% of APK）**。只算最初那四支，只有 7,464,216 B 解压 / 2,763,194 B 压缩（1.54%）——漏掉 `libshell` 就漏掉了真正的引擎。
- 其余 **86 个 .so**：解压 68,028,848 B、压缩 **28,193,229 B（15.72%）**，即 native 压缩体积的 **80%** 是第三方。大户：`libaudioeffect 7.5M`、`libime_net_sdk 6.9M`、`libsscronet 6.4M`、`libcurl 5.3M`、`liblynx 4.7M`、`libbarhopper_v3 4.4M`、`libmetasec_ml 4.0M`、`libttffmpeg 3.5M`（均为解压值）。

**res 的 33 MB 里，字体 24.3 MB（13.5% of APK）**：`9k.ttf` 18,553,272 B（**STORED，压不动**）、`bf.ttf` 9,049,892 → 5,695,051 B；另 970 张 PNG 合计 7,808,951 B（STORED）。

**dict 的 89.6 MB 内部**（压缩 / 解压）：
- 26 个哈希名散文件 75,197,962 / 152,210,934（41.92% of APK）
- `hw/`（手写）5 个文件 11,955,162 / 16,463,313（6.66%）
- `asr/` 3 个文件 2,466,829 / 7,258,426（1.38%）

【A】熵与字符串（均为读前 2 MB 采样）：`hw/micro/arm64/*.micro` 熵 6.80 bit/B、零字节 2%，是量化网络权重；`6ee457976f14` 里能直接读到 `Aarau`/`abaci`/`abhor` 等英文词条，是英文词典；其余散文件熵 5.3–6.3 bit/B、零字节 26–42%，是打包过的词典/语言模型，不是加密（加密不会保留这样的零分布）。【B】这是整理过的二进制容器，具体格式未解。

**哪些是必须的、哪些是附带的**：
- 必须：输入法自己的 .so（上段 6.85 MB）、dex 里能按语义认出的约 1,100 个产品类（`input` 768 + `doubaoime` 321；另有约 10,400 个类落在混淆顶层包里，无法归属【C】）、`assets/skin`（1.02 MB）、`dict` 里的中文词库。
- 可能可以砍：`9k.ttf` 18.5 MB 的内置全量 CJK 字体（系统字体 + 子集化能省掉绝大部分）、`lottie` 2.4 MB、扫码模型 0.88 MB。
- 明显是商务/运营：5 套推送/厂商通道（`com/xiaomi/push` 377、`com/huawei`（含 HMS 全家桶）527、`com/vivo` 235、`com/ss/android` 464、`com/bytedance/push` 115 个类）、账号 `larus/account`、验证码 `bdturing` 71、反馈 `feedbackerlib` 170、以及 20+ 个应用商店包名的升级检查。**它们在 dex 里占多少 MB 无法按包切分**（【C】：dex 是整体压缩，没有 per-package 大小），所以这里只给类数，不给 MB。

**包装选择**：`extractNativeLibs="true"`【A：manifest】，所以 .so 在 APK 里是 Deflate 而不是 STORED——用解压换体积（lib/ 从 85.7 MB 降到 35.0 MB），代价是安装时要解压、首次加载不能直接 mmap 页对齐的库。单人项目更该用 `extractNativeLibs="false"` + `zipalign`，省启动时间。

## 6. 不值得借鉴的

1. **24 个 ContentProvider、72 个 Service、72 个 Activity、42 个权限**，还有 26 个组件跑在 `:Setting` 进程、10 个 `:sandboxed_processN`、4 个 `:push`【A：manifest 统计】。每个 provider 都在冷启动路径上。
2. **把整个键盘 UI 用 C++ 重写**。75 个 `ui::` 类、54 个 `GetInterface` 工厂确实优雅，代价是：失去 Android Studio 布局预览、系统字体缩放要自己接（`style.xml` 里手写 `misans_medium_adaptive`）、无障碍与输入法框架的可见性语义要重做。单人项目用 Java View + 一份数据驱动的布局描述即可。
3. **四套 UI 容器并存**：native `ui::`、Lynx/Relax JS、WebView、anniex 卡片。每套都要自己的调试链路。
4. **内置 18.5 MB 且 STORED 的全量 CJK 字体**。子集化或直接用系统字体，是投入产出比最高的一刀。
5. **把类名压到 1–2 字符**（`input` 包 52%）。崩溃栈不可读、堆栈聚合失效，对单人维护是净损失。
6. **`libcurl` 与 Java QUIC 两条网络栈并存**。二选一，别都留。
7. **多进程推送/反馈**（`:push`、`:feedbacker` ×9）。没有推送需求就别引这套。

| 1 | dict 文件的确切格式 | **仍未解**。只能停在"有 marisa/protobuf 依赖、无 marisa magic"这一步；要定性得逆向 `libshell` 的词典加载函数 |
| 2 | `librvm.so` 的来源 | **已解，且原判断有误**。`librvm.so` 不是 `libkeyboard` 的依赖，是 **`librelax.so` 的 `DT_NEEDED`**（同批还有 `libclay.so`）。而 `librelax.so` 在输入法进程里**根本没被加载**：`/proc/<pid>/maps` 里只有 `libkeyboard.so`、`libshell.so` 这些，没有 relax/rvm/clay/lynx。APK 与设备上也都没有 `librvm.so`。所以它只影响 Relax 那条从未启动的路径 |
| 3 | 41 个 Java native 的注册方式 | **已解**。源码里 218 个 `native` 声明 = 176 个 `Jni_*` 导出 + **41 个"无导出、但方法名作为独立字符串出现在 .so 里"**（配合 `JNI_OnLoad` 存在，判为 `RegisterNatives`）+ 1 个 `getMessage`（导出与字符串都没有，多半是死声明） |
| 4 | `9k.ttf` / `bf.ttf` 的字体名 | **已解**。直接解析 TTF 的 `name` 表：`res/9k.ttf`(18.5MB) → **"Apple Color Emoji"**；`res/bf.ttf`(9.0MB) → **"Qihei for Doubao"**（青黑定制版）；`res/9U.ttf`(30.6KB) → **"oimeui"**；`res/c3.ttf`(1.9KB) 的 name 表解析失败，多半是子集/占位 |
| 5 | 混淆策略的原始 R8 规则 | **仍未解**。看不到 `-keep` 配置，只能从结果反推 |
| 6 | Relax 到底加载什么 | **部分解**。APK 的 assets 里**没有任何 `.js` / `.bundle`**，只有 `librelax*.so` 与 `liblynx*.so` 一整套 native；输入法进程也不加载 Relax。所以"Relax 用来做皮肤"在本机没有任何证据 |

## 8. 最值得借鉴的两条

1. **原生 UI 与平台后端分离**：`libkeyboard` 里 75 个 `ui::` 类不碰 Android API，平台能力由 722 KB 的 `libime_ui_android_platform.so` 提供（`GetFont/GetImage/GetWindow/GetTimer/GetAssets`）。绘制方向是反的：native 的 `nativeDraw` 回调进 `KeyboardView`，由 Java 的 `drawText/drawImage/drawRect/drawCircle` 画到 `Canvas`；`CreateView` 同样是 native 调 Java 去 `new KeyboardView`【A：两侧符号与方法体】。换渲染后端只需重写这 722 KB。单人项目的等价做法：把「布局计算 + 绘制指令」抽成纯 JVM 模块（本仓 `Geometry`/`GestureGate` 已经是这个路子），把「真正画」留在 View 层，两边用一组坐标/指令数据解耦——这样布局逻辑可以单元测试，换 Compose/WebView 也不用重写。
2. **布局与初始化都数据化 + 分帧**：键盘由 `assets/skin/**/*.xml` 描述（`ButtonEnglishChar` 带 `keycode`/`fusiyin_bubble_keycode` 等属性），首帧只建当前键盘、其余逐帧补齐（资源内注释原文）；初始化切成 `InitPeriod` + 空闲任务，字体预热异步且可回退。单人项目的等价做法：用一张 JSON/XML 描述键位与长按表（改键不用改代码），首帧只建可见部分，重组件（模型、字体、网络）统一走一个 `Lazy` 服务注册表，取不到就降级而不是崩。
