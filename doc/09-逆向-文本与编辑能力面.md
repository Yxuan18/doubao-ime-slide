## 二、逐组：参数、状态依赖、直接调用安全吗

### 1. 提交

`DoCommit(String commitStr, int type, String source, ...)` 是引擎自己对外的提交入口。
`type` 是 `CommitType.ordinal()`（`DEFAULT=0`、`UNDO_CLEAR=1`，392 行），`source` 是
`CommitSource` 里的字符串（`clipboard`、`common_phrase`、`toolbar_clipboard` …，376–388 行）。
证据：`KeyboardJni.java:2242` 用 `CommitType.DEFAULT.ordinal()` 构造 `t5.c` 请求，与 `DoCommit`
反汇编里拿 `CommitType.UNDO_CLEAR.ordinal()` 比较的分支一致（B）。

`DoCommit` 的 5 参重载在 jadx 里是"Method dump skipped"，用 `dexdump -d classes.dex` 读调用表，
它没有绕开标准通道：调用表里是 `beginBatchEdit`、`clearPreeditBeforeCommitIfNeeded`、
`setComposingRegion`/`setSelection`、`InputConnectionWrapper.commitText`、`endBatchEdit`（偏移
0x0388 处），并经过 `t5.b` 的拦截器链（日志字符串 `"[DoCommit] after interceptors commitLength: "`）。
`mImeService` 为空或 `InputConnection` 为空时打日志后 return（B，来自同一份反汇编的字符串与分支）。

- 参数：第一个是最终文本；第三个决定埋点来源，传错只影响报表。
- 需要 native 状态吗：不需要直接调 native，但它读 Java 侧缓存的预编辑/光标状态。
- 安全：这是全套里最安全的一条。它与用户点剪贴板面板走的是同一条路
  （`com/bytedance/android/input/keyboard/ClipboardHistory/ClipboardHistoryItemAdapter.java:309`、`com/bytedance/android/input/keyboard/commonphrase/CommonPhraseItemAdapter.java:153` 都是
  `DoCommit(str, 0, CommitSource.X)`），失败路径是打日志返回。

`commitString`/`commitSymbol`/`commitForSpace`/`commitForEnter` 是 native，语义绑定引擎当前的
候选/棋盘状态。`commitString` 在整个 Java 源码里**没有调用点**（未找到 Java caller，B），
说明它由 native 侧回调或已废弃；不要拿它当"往编辑框写一段字"的接口。`commitForSpace` 有 Java
调用点（`com/bytedance/android/input/keyboard/areacontrol/InputViewRoot.java:594`），返回 boolean，前提是引擎里真有候选/预编辑。

### 2. 删除

`backspaceClickEvent()` 是纯 Java：有选区就 `commitText("")`，否则删光标前 1 个字符，并同步
`AsrContext` 删除计数、`AutoSpaceDeleteGuide`、`j6.f` 的文本缓存；常用语输入框里改走
`sendKeyEvent(KEYCODE_DEL)`（1691–1780，B）。也就是说它不只是删字，还维护一串埋点与缓存。
模块若直接调它，这些计数器会被手势写入，报表数据被污染（C，依据是这些副作用就写在方法体里）。

`handleJavaBackspaceClickEvent()` / `handleJavaBackspaceForDoubleClick()` 是 native 回调，
Java 侧只在自己绘制的退格键被点时调（`com/bytedance/android/input/keyboard/areacontrol/InputViewRoot.java:582`、`com/bytedance/android/input/keyboard/handwriting/HandWritingBoardView.java:579`）。
在 26 键原生棋盘上调它们，等于让 native 以为"Java 退格键被按了"，与当前的真实按键来源不一致（C）。

`OnBackspaceTouchEvent(8 个 int)` 只是把参数转给 `BackspaceSwipeWindow`（1137），不是删除本身。

### 3. 清空

三条清空都在 Java 层，靠 `ImeService.k()` 拿 `InputConnectionWrapper`：

- `ClearText()`（678）：`getExtractedText` 取全文 → `setSelection(0, len)` → `commitText("")`
  → `deleteSurroundingText(MAX, MAX)`，返回被清掉的字符串。
- `ClearTextBeforeCommit(String)`（710）：清空后立刻写入新串，是"替换全文"。
- `ClearTextBeforeCursor()`（729）：只清光标之前；先读 `j6.f.i(MAX)` 缓存，空则回落到
  `getTextBeforeCursor(MAX)`；走回落分支时还会调 `setTextAfterCursor("")` 与 `InputView.L()`。

安全点：三者在 `mImeService`/`InputConnection` 为空时都直接 return（B）。
风险点：`ClearText()` 依赖 `getExtractedText`，返回 null 的编辑器（不少 WebView/自绘编辑框）
会静默什么都不做，只返回空串；`deleteSurroundingText(Integer.MAX_VALUE, …)` 在长文档上是
一次大范围删除，且 `getExtractedText` 会把整篇文本拉进内存（B，代码事实）。

`doUpClearAction(int, boolean)` 是 native，1=上滑清空、2=下滑撤回
（`com/bytedance/android/input/popup/BackspaceSwipeWindow.java:410/418`、`com/bytedance/android/input/keyboard/handwriting/HandWritingBoardView.java:550/556`）。它不是通用清空接口，
而是"退格键上滑"这个手势的实现；`getUpClearCondition()` 返回位掩码（bit0 上滑清空、bit1 下滑撤回，
`com/bytedance/android/input/popup/BackspaceSwipeWindow.java:491` 起）。

### 4. 预编辑

`UpdatePreedit(String)` → `updatePreeditWithResult`；`SetPreeditRange(before, after)` 调
`setComposingRegion`；`finishPreedit(boolean)` 落盘组合串；`getPreeditText()` 读
`SelectionTracker` 缓存的组合文本（2362）。全部依赖 `mImeService` 与其 `SelectionTracker`，为空时
return 0/""（B）。这些是引擎组合态的实现细节，模块不该写它们，只该读 `hasPreedit()` 做前置判断。

### 5. 剪贴板历史

- `getClipboardHistoryCount()`：条数。
- `getClipboardHistoryItem(position, 1)`：返回 JSON 字符串，字段 `phrase`
  （`com/bytedance/android/input/keyboard/ClipboardHistory/c.java:71` 是调用点，`:77` 解析）。第二个参数所有调用点都传 1，含义**未证实**（C）。
- `insertClipboardHistory(text, historyEnabled, false)`：这是**写入历史**，不是粘贴
  （`s5/e.java:478`，第二个布尔直接来自 `enable_clipboard_history` 设置）。
- `deleteClipboardHistory(phrase)` 按文本删；`clearClipboardHistory()` 清空；返回 int 状态。

开关：`enable_clipboard_history` 的默认值是 `false`（`res/xml/settings_preferences.xml:132`，
键在 133 行），`is_set_clipboard_history` 也是 `false`（136–137 行），"候选栏展示"
`enable_clipboard_candidate_bar_show` 默认 `true`（128–129 行）（A，资源文件）。所以**默认装机状态下历史是空的**，模块必须先读开关或先读 count 再决定
要不要把这条手势暴露出来。读取方式：进程内直接 `SettingsConfigNext.d("enable_clipboard_history")`
（键就是 `R.string.enable_clipboard_history` 的值，字符串与键同名，见 `res/values/strings.xml:414`），
不必走 `SettingsContentProvider`（provider 受 signatureOrSystem 保护，模块在同一进程里用不上它）。

### 6. 常用语

`getCommonPhraseItem(position, 1)` 返回 JSON `{phrase, input}`（`com/bytedance/android/input/keyboard/commonphrase/a.java:64–73`）；
上屏同样走 `DoCommit(str, 0, CommitSource.COMMON_PHRASE)`。`insertCommonPhrase(code, phrase)`
是新增，返回 2 成功、4 数量超限（`com/bytedance/android/input/keyboard/commonphrase/a.java:83–88`）。没有找到常用语的总开关，
`CommonPhraseView.b()` 里参与可见性判断的是 `full_base_input_mode` 与 `enable_clipboard_history`
（`com/bytedance/android/input/keyboard/commonphrase/CommonPhraseView.java:133–165`），方向未确认（C）。

### 7. 联想

`getAssociations()` 返回当前联想词数组（`KeyboardJni.java:1133` 直接塞给 UI）；
`doAssociations(String)` 按来源重新取（`l4/a.java:57` 传 `"send"`）；`setAssociationEnabled(boolean)`
是开关；`isAssociate()` 表示"当前处于联想态"。联想词的上屏没有专门方法，仍走 `DoCommit`。
对模块价值低：联想本来就在候选栏，手势替代不了"选哪一个"。

### 8. 光标

`enterMoveCursorMode()` 是工具箱里"移动光标"那一项的入口（`com/bytedance/android/input/keyboard/areacontrol/y.java:208`，工具项 case 16），
进的是整套触摸板模式，不是单步移动。`ShiftCursor(int)` 转给
`CursorMoveController.l(service, i)`，落到 `sendDownUpKeyEvents(21 或 22)`，即发左右方向键
（`com/bytedance/android/input/cursor/CursorMoveController.java:676`），并维护 selection 追踪状态（B）。
`isMoveCursorModeSupported()` 是前置能力位。单步移动若直接调 `ShiftCursor`，会绕过 native 的模式状态，
是否被接受**未证实**（C）。

## 四、撤销无效：源码能解释到什么程度

1. **豆包自己没有任何一处调 `performContextMenuAction(undo)`。** 全源码里 `performContextMenuAction`
   只有三处调用：`R.id.selectAll` 两次（`KeyboardJni.java:1378`、`:4488`）和 `R.id.paste`
   一次（`o5/e.java:555`）。`16908338`/`16908339`/`R.id.undo`/`R.id.redo` 在反编译源码里
   一次都没出现（B，grep 结果）。所以"豆包自己的撤销按钮"走的是另一条路。
2. **豆包的撤回是 native 的"清空恢复"，不是编辑器撤销。** 上滑退格清空、下滑退格撤回，两个方向
   分别落到 `doUpClearAction(1)` 与 `doUpClearAction(2)`（`com/bytedance/android/input/popup/BackspaceSwipeWindow.java:410/418`）。
   native 侧保存的是 `InputBoxScreenModel::last_upclear_text_`、`GetLastUpClearText()`、
   `DataClearForLastUpClear()`、`UpClearValid()`（`libkeyboard.so` 符号表，B）。
   它恢复的是**豆包自己清掉的那段文本**，与编辑器的撤销栈没有关系。
   `com/bytedance/android/input/keyboard/handwriting/HandWritingBoardView.java:550–556` 里清空后 `setToolbarRevocationButtonVisible(true)`，
   那个"撤回"按钮同样是这条路径。
3. **`CommitType.UNDO_CLEAR` 不是撤销实现。** 它只是给"清空后重新提交"打的一个标记
   （`DoCommit` 反汇编里比较 `UNDO_CLEAR.ordinal()` 后写 `"undo_clear"` 字符串），不执行回滚（B）。
4. **`performContextMenuAction(16908338)` 返回 true 不代表发生了撤销。** AOSP 里
   `com.android.internal.inputmethod.EditableInputConnection.performContextMenuAction` 是：

   ```java
   mTextView.beginBatchEdit();
   // ...（此处略去一行 DEBUG 日志）
   mTextView.onTextContextMenuItem(id);
   mTextView.endBatchEdit();
   return true;
   ```

   而 `TextView.onTextContextMenuItem` 的 `case ID_UNDO` 注释写着 `// Returns true even if
   nothing was undone.`（AOSP master，B）。也就是说：通道返回 true 只说明"调用被受理"。
   小米笔记的编辑框如果不是 `TextView`（或撤销被 `allowUndo` 关掉 / 撤销栈不含 IME 提交的编辑），
   就一定表现为"true 但无变化"（C，依据是返回值的语义与 ACCEPTANCE 第 8 项的现象）。

**结论**：现有 Z 手势在小米笔记无效，机制上有解释——豆包自己不用这条通道，而这条通道的返回值
不携带"是否真的撤销"的信息；真正可用的撤销是引擎的清空恢复，且只对它自己清掉的文本有效。
模块没有可复用的引擎侧通用撤销。

## 五、风险面

1. **实例 native 方法只能在 `KeyboardJni.getKeyboardJni()` 返回的那个对象上调。**
   `mKbdJni` 在静态初始化块里、`System.loadLibrary` 之后才 `new` 出来（`KeyboardJni.java:590`），
   native 指针绑在那个实例上。反射 `new` 一个 `KeyboardJni` 再调 native 方法会让输入法进程崩溃
   （与 `CLAUDE.md` 里已记录的实测一致，A）。模块要用 Xposed 拿 `mKbdJni` 字段或调
   `getKeyboardJni()`，且必须用键盘进程的 ClassLoader。
2. **`mImeService` 由 native 侧回调 `SetImeService` 写入**（Java 里没有调用点，B）。所以
   `DoCommit`/`ClearText*`/`backspaceClickEvent` 这些 Java 路径依赖它非空；为空时是静默 no-op，
   不会崩，但手势会"看起来没反应"。
3. **预编辑残留。** 模块的手势发生在原生棋盘上，用户可能已经打了一串拼音没上屏。
   `DoCommit`/`ClearTextBeforeCommit` 会先 `clearPreeditBeforeCommitIfNeeded`，相对安全；
   模块现有的粘贴兜底是 `ic.commitText(text, 1)`（`Actions.java`），不经过这一步，
   有未上屏拼音时组合区与编辑框可能不同步（C）。`ClearText` 这类方法则是在引擎不知情的情况下
   改文本，候选/联想仍按旧上下文刷新（C）。要清空时优先用引擎路径，而不是自己
   `deleteSurroundingText`。
4. **UI 类 native 会改版面。** `enterMoveCursorMode`/`exitMoveCursorMode`/`doUpClearAction`
   会切键盘状态或弹窗，而模块的手势状态机（`GestureGate`）正处在一次按下中间；两者叠加会让
   后续 MOVE/UP 落到新棋盘上。要么拒绝在未完成手势时调用，要么只调纯文本路径（C）。
5. **线程。** 模块的钩子在 `nativeTouch` 上，与输入法 UI 线程同一条（A，模块架构决定）。
   但若从别处（比如设置页或后台线程）调这些方法，`InputConnection` 与 View 操作都不合法（C）。
6. **大文本。** `ClearText` 会 `getExtractedText` 拉全文；在长文档/大输入框上有内存与耗时风险（B）。
