# 06 逆向总览：这份材料能拿模块怎么办

对象：豆包输入法 1.5.3（`com.bytedance.android.doubaoime`，versionCode 100503006，targetSdk 37）。
目的：把反编译 + 运行时观测的结果，变成对 `app.xuan.doubaoslide` 有用的判断——
哪些东西值得做、哪些是坑、哪些只是好看。

细节在 07–11 五份分册。**这一份只做裁决**：排优先级、指出互相冲突的结论、划出不做的边界。

## 1. 方法与证据基础

- 反编译：jadx 1.5.1，`apk/base.apk`（179 MB）→ 23,419 个 `.java`，17,601 个类，
  30 个类反编译失败（进度 99% 后 `finished with errors, count: 30`）。失败的类名见各分册。
- 运行时材料：`/tmp/doubao-ime/` 下的 `jni_methods.log`（Frida 枚举的方法全表）、
  `kv.log`（KeyboardView 字段）、`views.log`、`layout.log`、`recon1.out.txt`，以及既有
  `ACCEPTANCE.md` 的实测记录。
- **本轮没有新增 A 级运行时证据**：设备在开工约十分钟后离线（`adb devices` 为空），
  此后所有结论都来自静态源码、资源、二进制符号。凡标 A 的，都是既有实测或资源里的常量事实。

证据等级沿用仓内约定：**A** = 运行时实测 / 直接读到的代码或资源事实；
**B** = 反编译可见、未运行验证；**C** = 推断（写明依据）。

### 1.1 三处需要更正的流传前提

写分册时发现，任务书里我给的三个前提是错的。更正如下，后续引用以这里为准：

| 流传的说法 | 实际 | 依据 |
|---|---|---|
| `KeyboardJni` 有 618 个 static native 方法 | 618 是 Frida 枚举到的**全部**方法（含 Java 包装层）；其中 **217 个是 `native` 实例方法** | 10 号分册 §0 |
| 引擎在 `libkeyboard.so` | 引擎在 **`libshell.so`**（8.9 MB），导出 `oime_engine::`、`shell::InputState`；`libkeyboard.so` 的 `DT_NEEDED` 第一项就是它 | 10 号分册 §1.1 |
| `lib/arm64-v8a/` 只有 4 个 `.so`，共 7.1 MB | APK 里共 **93 个 `.so`**，解压 85.7 MB；自家 7 支仅 6.9 MB（3.82%），其余 86 个第三方占 28.2 MB（15.72%） | 10 号分册 §5 |

另有一处是 11 号分册写错、这里更正：

- **`FLAG_IGNORE_VIEW_SETTING` 只绕过 View 自己的 `isHapticFeedbackEnabled`，不绕过系统级
  触感开关**（绕过系统级需要 `FLAG_IGNORE_GLOBAL_SETTING`）。所以模块
  `Actions.haptic` 的问题是"不看豆包的 `enable_key_vibrate`（默认关）"，不是
  "不看系统开关"。建议据此缩小（`Actions.java:244–255`，A：源码）。

## 2. 一页结论

### 2.1 先做（收益明确、风险可控、能在真机上验证）

| # | 做什么 | 为什么值得 | 主要风险 | 升到 A 需要 |
|---|---|---|---|---|
| 1 | **Z 手势换掉**：现在这条通道在部分应用里静默无效，且返回值不携带信息 | 见 2.2——这不是"兼容性问题"，是这条 API 本身就没保证 | 换成什么还没定；引擎侧没有通用撤销 | 先确认目标应用里哪条路径真能用 |
| 2 | **触感遵循豆包的按键震动开关** | 豆包默认关震动，模块无条件振，等于无视用户做过的选择 | 读 `SettingsConfigNext` 是本地缓存，可能与运行态不同步 | 2×2 矩阵（豆包开关 × 系统触感）各滑 5 次 |
| 3 | **死区的可感知化**：12px 容不下点击抖动，且 DEAD 零输出 | 现在是"按了没反应"的最短路径，最容易被当成故障 | 提高门槛会改变已标定的判定，需重新跑阈值边界单测 | 0–72px 横扫脚本 + 触感区分 |
| 4 | **几何的顶部带从常量换成运行时值** | `STRIP_FRAC = 151/909` 只在一台机器的一个版面成立；横屏 `padding1x="0,50,0,0"`、悬浮 `2,45,2,0` | `getToolbarHeight()` 的口径未验证；另有 151 vs 171 的 20px 未解释（见 §3） | 先真机打一行 `getToolbarHeight()` 与 151 对照，对不上就退回只解析布局 XML |

### 2.2 关于 Z（撤销）：这条不是 bug，是选错了 API

09 号分册找到的解释，我复核后认为是成立的：

- 豆包自己**从来不用** `performContextMenuAction(undo)`。全源码里这个 API 只有三处调用：
  两次 `selectAll`、一次 `paste`。`16908338` / `R.id.undo` 一次都没出现（B：grep 全量源码）。
- 豆包的"撤回"是 native 的**清空恢复**：`doUpClearAction(1/2)` 配
  `InputBoxScreenModel::last_upclear_text_`，只恢复它自己清掉的那段文本，与编辑器撤销栈无关。
- AOSP 的 `EditableInputConnection.performContextMenuAction` **无条件 `return true`**，
  `TextView.onTextContextMenuItem` 的 `ID_UNDO` 分支注释原文写着 "Returns true even if
  nothing was undone."。所以模块日志里的 `ok=true` 从来不表示"真的撤销了"。

**这条对验收纪律的影响**：`ACCEPTANCE.md` 里所有以 `ok=true` 作为通过判据的动作项，
都需要改成"看输入框文本变了没有"。复制/粘贴/剪切/全选还有文本可验；撤销没有。

### 2.3 再看（有价值，但前置条件多）

| 候选 | 前置条件 | 判断 |
|---|---|---|
| **多段粘贴**（`getClipboardHistoryCount/Item` + `DoCommit`） | `enable_clipboard_history` 默认 **false**，默认装机历史为空；`DoCommit` 会走拦截器链、刷新联想、打埋点 | 值得做，但必须先读开关、空列表要有降级。这是现有 InputConnection 通道**做不到**的事，是真正的新能力 |
| **常用语上屏** | 数量上限 500，顺序由引擎给 | 同上；对长串（地址、证件号）收益最大 |
| **清空输入框** | `ClearText` 依赖 `getExtractedText`，部分编辑器返回 null 时静默无效 | 可以做成手势 + 模块侧快照回填（它自己返回被清文本） |
| **`preHandleTouchEvent` 旁路观测** | 手写棋盘上会被调用两次；返回非 null 会让键盘失聪 | 只做"记录不返回"，用来查清候选栏那 171px 到底有没有进 `nativeTouch` |
| **`backspaceClickEvent`** | 是静态入口，与"禁止无实例调用 KeyboardJni"的硬约束冲突 | 有实例时可以试；删除类动作的现成动作层 |

### 2.4 不做

| 不做 | 理由 |
|---|---|
| 重造光标滑动 | native 已有 `ui::Slider` / `cursor_slide`，在空格上横拖就能移光标。模块再造一套只会和它抢事件 |
| 往键盘上叠自绘提示（箭头、轨迹线） | 键盘是 native 自绘位图，叠 View 会和候选栏、浮层抢层级；每次版面变化都要重新标定 |
| 主动 `switchKeyboard` 做自检 | 会打断用户输入，只能用在测试构建里，不能进正式路径 |
| 用 `SettingsContentProvider` | 受 `signatureOrSystem` 权限保护，外部调不到；进程内直接读 `SettingsConfigNext` 就够了 |
| 把 DEAD（死区）改成补发轻点 | 等于用误输入换反馈，与死区存在的理由冲突 |

## 3. 四个必须先解决的技术债

这四条不解决，上面任何一条扩展都不稳。

1. **顶部带 151 还是 171。** `Geometry.STRIP_FRAC = 151/909` 是模块自己测的；
   `views.log` 里 Java 候选栏高 **171**。差 20px。要么 native 自绘候选带与 Java 候选栏高度
   本来就不同，要么两次测量不在同一个版面。**这是当前几何最不确定的一个数**（C：现象清楚，
   机制未定）。
2. **棋盘号 11–14 的语义冲突。** `InputBoardType` 枚举顺序与设置页/工具栏里的 `target`
   对不上（设置页写 `target="11"`，枚举 11 是 `kStroke`；工具栏"更多候选"写 12，枚举 12 是
   `kBoardSwitch`）。**不要按枚举硬编码**，否则符号页会被当成笔画页（08 §7.1）。
3. **候选栏触摸是否污染手势判定。** `KeyboardView` `bringToFront()` 之后覆盖了候选栏那
   171px，靠 `InputViewRoot.setupKeyboardCandidateTouchForwarding` 转发。那个方法
   （547 条指令）反编译失败，返回 true 还是 false 未知。若为 false，候选栏点击会同时进
   `nativeTouch`（07 §6）。
4. **`ok=true` 不等于成功。** 见 §2.2。验收判据要改成看文本。

## 5. 认账：被放弃的方向

1. **不把 `HAND_BACK_MS` 降到 150ms。** 11 号分册建议降到 150ms，理由是"引擎 500ms 长按
   减去 350–450ms 绘制延迟"。这个推导与 `doc/01` 的实测调用序列冲突：浮层第二格是由引擎
   **501ms 发出的 LEAVE** 触发的，不是 350–450ms 的绘制延迟。按实测，映射键浮层 ≈
   `归还时刻 + 500ms`，当前是 800ms，未映射键是 500ms，差 300ms。
   降到 150ms 能把这 300ms 压到 150ms，但**与"普通下滑从按下到越过 60px 通常不到 200ms"
   直接冲突**——150ms 会把相当一部分正常下滑误判成长按，产生多余的 DOWN + CANCEL。
   **结论：先测下滑时长分布，再定 200–250ms 之间的值。** 没有分布数据之前不动这个常数。
2. **不按"618 个 native 方法"来规划能力面。** 实际是 217 个 native 实例方法 + Java 包装层；
   按 618 去估工作量会高估三倍。
3. **不做"先查轮子"的结论。** 本轮两次网络检索（Xposed 输入法手势模块 / LSPosed 键盘手势
   快捷键）都返回空结果，无法据此声称"业界没有类似实现"。这一项保持开放，不写成结论。

## 6. 未证实（跨分册汇总，按影响排序）

1. 顶部带 151 vs 171 的 20px（§3.1）——影响所有几何判定。
2. 棋盘号 11–14 的真实语义（§3.2）——影响 `BoardGuard` 的武装范围。
3. 候选栏触摸是否会进 `nativeTouch`（§3.3）——若会，现有手势判定有污染源。
4. `getToolbarHeight()` 的单位与口径——决定 §2.1 第 4 条能不能落地。
5. 剪贴板历史/常用语在默认装机下的实际可用性（默认开关为关）。
6. 小米笔记编辑框是不是 `TextView`——决定撤销无效到底是"通道没保证"还是"实现不支持"。

## 7. 清洁交接

- **假设**：以上全部基于豆包输入法 1.5.3 的静态代码与既有运行时记录；版本一变，方法名与
  枚举顺序都可能失效，引用前先核 `versionName`。
- **下一步的最小验证**：插上设备，跑三行——`getToolbarHeight()` 的值、`getCurrentKbdType()`
  在符号面/数字面的返回值、一次候选栏点击是否产生 `nativeTouch` 日志。这三行能同时解掉
  未证实 1、2、3、4。
- **谁负责**：下一轮改手势行为之前，先读本文件的 §2.1 与 §3；改动结论补进 `ACCEPTANCE.md`。
