# 调试与验收手册

`CLAUDE.md` 的参考附录：命令、探针、取证配方与历史说明。
主线只留"必须先做什么"，具体怎么做、为什么这么做都在这里。
动手排障前不需要通读，遇到对不上号的时候再来查。

---

## 一、装机环节的三个坑

- **`su -c` 里别套引号和转义。** 管道本身没问题（`grep -a DoubaoSlide … | tail -5` 是好的），
  但 `grep -a 'x|y'`、`grep -aiE "a|b"` 这类内层引号会被吃掉，症状是 `unexpected '('`
  或把每个词当文件名。多条件用 `grep -e x -e y`，或者拆成多次 `su -c`。
  同理 `su -c 'a || b'` 会被解析成错误参数，症状是假的 "Permission denied"。
- **force-stop 默认输入法会让系统回退到另一个输入法。** 紧跟的 `ime set` 负责改回来；
  漏了就是"键盘没了"。
- **重装 APK 不会自动重载代码。** LSPosed 会弹「已安装」通知，模块开关状态保留，
  但输入法进程必须重启（`am force-stop` + `ime set`）才会加载新版本。

还有一个容易忽略的：**IME 重启会换日志文件**。`modules_*.log` 按进程创建时间新建，
拿"最新的那个"要在每次重启后重新 `ls -t`，不能沿用上一次的路径。

## 二、证据走文本

证据优先走文本：模块日志、`logcat`、`dumpsys`、`uiautomator dump`、编译与测试结果。

| 要确认的事 | 纯文本怎么确认 |
|---|---|
| 这一下按到了哪个键 | `Log.DEBUG=true` 构建，读 `DOWN <x>,<y> view=<w>x<h> 字母=<c>` |
| 手势被判成什么 | 读 `手势 c -> copy ok=true dy=…` / `手势作废：…` / `补发手势：…` / `长按归还：…` / `撤回预编辑：…` |
| 输入框里现在有什么字 | `adb shell uiautomator dump /sdcard/ui.xml` 后 grep 编辑框的 `text`（MIUI 笔记正文是 WebView，dump 不到；用**标题**那个原生 EditText） |
| 当前输入法是哪个、在不在 | `adb shell su -c 'dumpsys input_method \| grep -m2 -e mCurId -e mCurMethodId'` |
| 当前前台页面 | `adb shell su -c 'dumpsys activity \| grep -m1 mCurrentFocus'` |
| 多指有没有被识别 | 有 `多指输入：本次手势不判快捷键`、且**没有** `手势 … -> …` |
| 引擎的调用链差异 | 临时 hook `KeyboardView` 的方法（`onTouchEvent` / `preHandleTouchEvent` / `delaySendLongPressMessage` / `nativeTouch` / `drawTouchTipBubble`），打调用序列；查完删掉 |

常用命令：

```bash
# 测试手势（需 root）
adb shell su -c 'input swipe <x> <y1> <x> <y2> <duration_ms>'
# 读日志（每次 IME 重启后先重新选最新的那个文件）
LOG=$(adb shell su -c 'ls -t /data/adb/lspd/log/modules_*.log' | head -1)
adb shell su -c "grep -a DoubaoSlide $LOG | tail -20"
```

`input motionevent` 可以逐条注入 DOWN / MOVE / UP，用来精确控制时序；但它**注不出真多指**
（系统会把第一根手指转成 `action=3`），多指路径只能靠真手指验。

## 三、必须用截屏时的取证方式

只有被测对象本身是渲染结果时才截屏——native 自绘的长按浮层就是这种：`uiautomator dump`
的树里没有它，它也不产生任何日志。（2026-10-26 晚为长按浮层那条 bug 放开。）

1. 同一构建、同一脚本、同一个键各拍「基准帧」和「按住中的帧」；
2. `ffmpeg -i base.png -i target.png -filter_complex "[0:v][1:v]blend=all_mode=difference,format=gray,crop=1080:<h>:0:<y>,scale=<w>:<rows>"` 转灰度差分；
3. 打印成 ASCII 折线，比对**形态**，不比对像素计数。

**为什么强调形态而不是计数**：浮层里画着字母，`b` 和 `c` 的笔画数不同，同一个浮层的
"变化像素数"会差一截——按计数判"弹框在不在"会得出假阴性。

**裁剪窗口必须跟着被按的键走**：浮层出现在**被按键的正上方**，不是固定在候选栏。
窗口选错会量到别的东西（组合预览气泡、候选栏文字、按键高亮），据此下的结论全是错的。
这一条是 2026-10-26 绕远路的直接原因：窗口固定在 `t` 的位置，`c` 的浮层被裁在窗外，
于是得出了"完全没有浮层"的结论，并据此否掉了一个正确的实现。

**先校准通道再下结论**：阳性对照（未映射键，一定有浮层）、阴性对照（确定没有浮层的场景）
各跑一次，通道可信了再测未知。

## 四、做不到的要明说

触感反馈、选中高亮、候选栏长相、键位视觉对齐——这些是渲染结果，差分折线也只证
"形状对不对"，证不了"用户看到的样子对不对"。它们不算已验收，写进 `ACCEPTANCE.md`
的受限项，不要为了"确认一下"退回逐张看图。

## 五、闭环与标定

**闭环**：改代码 → 编译 → 安装 → 触发一次 → 读日志或控件树 → 下结论。
满足验证条件就停手，不反复戳手机。

**标定**：`nativeTouch` 收的是视图局部坐标。候选栏/工具条出现时键盘在**屏幕上**的位置
会变，屏幕坐标不能直接当视图坐标用（本机视图 1080×909、顶边在屏幕 y=1401）。
视图内部布局的实测结论见 `ACCEPTANCE.md` 第四节——2026-10-26 的复测里，带与不带候选栏
都是 `view=1080x909` 且 `字母=c` 不变。所以别把"整体上移并改变键宽"当成既定事实，
**以 `DOWN … view=… 字母=…` 那一行为准**。

## 六、证据介质的变更史

`ACCEPTANCE.md` 里 2026-10-26 之前的条目按当时的标准引用过截屏，保留不改；
第 21 项起只用文本证据；第 26 项起（长按浮层）按第三节的差分方式取证。

规则从"完全不看图"放宽到"渲染类可以截屏、但必须走差分"，是因为那条 bug 的对象
恰好是纯渲染的；放宽的同时把取证方式钉死，避免退化成肉眼读图。
